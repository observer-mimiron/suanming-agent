# Decision Dimension Selection Guide

按决策类型选择评分维度。不要求每次决策都用全维度——选 3-5 个最相关的。

## Library/Framework Selection (选库/选框架)

| 维度 | 评分标准 |
|------|---------|
| 功能匹配度 | 库提供的能力 vs 项目需求的匹配程度 |
| 改动量 | 接入所需修改的文件数和代码行数 |
| 社区健康度 | Stars/维护频率/issue 响应速度/Go 版本兼容性 |
| 学习曲线 | 从现有技术栈迁移到该库的认知成本 |
| 切换成本 | 未来若需替换该库，迁移代价多高 |
| 性能影响 | 对关键路径 (八字计算、API 响应) 的延迟/内存影响 |

## Protocol/Communication Selection (选协议/通信方式)

| 维度 | 评分标准 |
|------|---------|
| 与现有栈的兼容性 | 是否需要新增依赖/更改构建流程 |
| 类型安全 | 是否有 schema/契约保证 (protobuf/OpenAPI) |
| 调试便利性 | curl/postman 测试是否方便 |
| 性能特征 | 延迟/吞吐/连接复用/序列化开销 |
| 流式支持 | 是否原生支持 streaming (SSE/gRPC stream) |
| 运维复杂度 | 是否需要额外进程 (broker/proxy/service mesh) |

## Architecture Pattern Selection (选架构模式)

| 维度 | 评分标准 |
|------|---------|
| 实现复杂度 | 需要新增的抽象层数、代码结构变化 |
| 可测试性 | 单元测试/集成测试的隔离难度 |
| 未来扩展点 | 后续功能 (缓存/权限/多租户) 的扩展成本 |
| 现有代码破坏度 | 需要重构的现有模块数量 |
| 学习成本 | 团队/自己理解该模式的时间 |

## Database/Schema Change (改数据结构)

| 维度 | 评分标准 |
|------|---------|
| 迁移复杂度 | DDL 变更量、是否需要数据回填 |
| 查询模式匹配 | 新结构对现有查询的影响 (JOIN 增多/索引变化) |
| 回滚难度 | 出问题后能否安全回滚 |
| 存储开销 | 新增字段/表的磁盘和内存增量 |

## Risk Assessment Notation

风险列使用三段式：`概率/影响/原因`

- 概率：低 (几乎不会发生) / 中 (可能发生) / 高 (大概率发生)
- 影响：低 (轻微不便) / 中 (需要修复但不阻塞) / 高 (阻塞核心功能或造成数据问题)
- 原因：可选，≤10 字关键词。如「下游不兼容」「并发窗口」「精度不足」

不要用孤立的数字评分 (如 RPN=12)——数字无法支撑决策推理。
