# 命理大师 — 长期咨询型系统演进计划

**版本：** v1.0  
**日期：** 2026-06-10

---

## 1. 目标

命理大师的最终目标不是一次性排盘工具，而是一个**长期咨询型命理系统**。

它要支持的不是单轮“帮我算一下”，而是长期关系：

- 用户今天问事业
- 下周继续追问
- 下个月回来复盘建议
- 系统记得用户资料、历史问题、过往建议和上下文变化

一句话定义：

**一个能持续记住用户、围绕主题长期回答问题、并能跟踪建议演化的命理咨询 Agent。**

---

## 2. 为什么现在要单独写这份文档

当前 v1 主线已经明确为：

- Go / Eino
- 单 Agent + 多 Tool
- 项目知识库 MCP
- 问题驱动的排盘 + 问答

但这套主线目前只覆盖：

- 会话内追问
- 当前命盘复用
- 资料修正后重排

它还**没有真正覆盖**：

- 历史问题
- 过往建议
- 主题化咨询线程
- 跨会话连续咨询
- 长期用户画像

所以需要一份单独的长期演进文档，把未来怎么一步步长成真正的长期咨询系统定下来。

---

## 3. 最终产品形态

未来目标不是“会算命”，而是“会长期陪你咨询命理问题”。

系统最终应具备：

- 稳定的用户画像
- 可复用的命盘档案
- 长期咨询历史
- 主题化问题线程
- 可追踪的建议记录
- 周期性的建议更新

最终体验示例：

```text
第 1 次：
用户：我想看看事业运
系统：完成排盘，给出事业建议 A/B/C

第 2 次（隔一周）：
用户：上次你说我今年上半年要保守一点，那下半年呢？
系统：读取历史建议和当前问题，给出衔接性回答

第 3 次（隔一个月）：
用户：我最近在考虑换工作，这和你之前说的方向一致吗？
系统：基于历史建议、当前主题、命盘和知识检索给出判断
```

---

## 4. 系统演进总路线

```text
V1  会话内咨询
V1.5  跨会话用户档案
V2  主题化长期咨询
V3  LangGraph 对照版
V4  多体系命理顾问平台
```

原则：

- 先补 **memory model**
- 再补 **咨询线程模型**
- 再补 **复杂状态编排**
- 最后才考虑 **更重的 multi-agent**

---

## 5. V1：会话内咨询

### 目标

先把“排盘 + 问答”做通。

### 能力范围

- 收集出生资料
- 完成排盘
- 检索项目知识库 MCP
- 围绕当前问题生成回答
- 同一会话内追问复用命盘

### 当前限制

- 不记跨会话历史
- 不记过往建议
- 没有主题线程
- 只有会话内上下文

### 架构

- 单 Agent + 多 Tool
- Go bounded state machine
- 项目知识库 MCP

---

## 6. V1.5：跨会话用户档案

### 目标

从“会话型系统”升级成“认识这个用户的系统”。

### 要补的核心对象

#### `UserProfile`

稳定用户资料：

- 出生信息
- 性别
- 历法偏好
- 时区
- 资料可信度

#### `BaziProfile`

排盘档案：

- 命盘结果
- 计算时间
- 资料版本
- 是否为当前有效命盘

#### `ConsultSession`

一次咨询会话：

- 起止时间
- 会话问题列表
- 主要结论摘要

### 价值

- 用户不用每次重新输入出生资料
- 系统能跨会话复用命盘
- 为长期咨询打底

### 架构影响

- 需要从内存状态切到持久化
- 不需要马上改成 LangGraph

---

## 7. V2：主题化长期咨询

### 目标

从“记住用户”升级成“记住用户在问什么，以及之前怎么回答的”。

### 要补的核心对象

#### `ConsultTopic`

主题线程，例如：

- 事业
- 婚恋
- 财运
- 健康

字段建议：

- `topic_id`
- `user_id`
- `topic_type`
- `status`
- `summary`
- `last_active_at`

#### `QuestionRecord`

每次具体问题：

- 用户原问题
- 系统识别出的意图
- 所属主题
- 是否依赖历史上下文

#### `AdviceRecord`

每次建议沉淀成结构化记录：

- 建议内容
- 适用主题
- 依据摘要
- 来源引用
- 时间点
- 生效条件
- 后续可追问点

### 价值

系统不再只是“记住命盘”，而是开始记住：

- 你之前问过什么
- 我之前怎么答的
- 为什么这么答
- 这次问题和上次是什么关系

### 架构影响

这里开始真正进入“长期咨询系统”。

这一步依然可以先用 Go 主线实现，但复杂度已经明显上升。

---

## 8. V3：LangGraph 对照版

### 目标

当长期咨询状态开始复杂后，用 LangGraph 对照版验证：

- planner 是否比 Go 状态机更清晰
- conditional edges 是否更适合长期咨询分支
- bounded loop 是否让追问流程更自然

### 适合引入 LangGraph 的地方

- 用户资料冲突修正
- 多主题路由
- 问题与历史建议的关联判断
- 是否需要重排盘
- 是否需要追问补资料
- 是否进入建议更新流程

### 推荐节点

- `profile_resolver`
- `topic_router`
- `history_reader`
- `advice_planner`
- `response_planner`

### 不建议一开始就做

- 开放式 autonomous loop
- manager / supervisor
- 多 agent 自反思闭环

---

## 9. V4：多体系命理顾问平台

### 目标

只有当产品从“八字咨询”扩成“多命理体系平台”时，才考虑更复杂架构。

### 可能扩展的领域

- 八字
- 六爻
- 紫微
- 姓名分析
- 合婚
- 择日

### 到这一步才值得考虑

- skill-based architecture
- specialist routing
- manager / supervisor
- 多领域上下文隔离

原因：

这时不同能力域已经真的像不同 specialist 了，而不是人为拆分。

## 11. Agent 架构升级条件

不要因为“想学”就升级架构，应该满足以下条件才升级：

### 升级到长期咨询 memory-first 架构的条件

- 用户确实需要跨会话继续追问
- 系统需要复用历史建议
- 单次回答不足以承载产品价值

### 升级到 LangGraph 的条件

- Go 手写状态机开始变得难维护
- 条件边明显增加
- 追问分支变复杂
- 想要可视化 reasoning flow

### 升级到 manager / multi-agent 的条件

- 出现多个独立命理体系
- 不同 specialist 有清晰边界
- 单一 agent 已经难以维护

---

## 12. 每阶段完成标准

### V1 完成标准

- 能排盘
- 能回答问题
- 能会话内追问

### V1.5 完成标准

- 跨会话记住用户资料
- 默认复用历史命盘

### V2 完成标准

- 有主题化咨询线程
- 有结构化建议记录
- 能基于历史建议继续回答

### V3 完成标准

- LangGraph 对照版能清晰展示比 Go 状态机更适合的部分

### V4 完成标准

- 多命理体系路由清晰
- skill / specialist 拆分自然合理

---

## 13. 当前结论

你这个项目如果真要做“长期咨询型系统”，核心不是先补多 Agent，而是先补：

1. 用户档案
2. 命盘档案
3. 咨询主题线程
4. 历史问题记录
5. 建议记录

一句话总结：

**长期咨询系统的第一优先级是 memory model，不是 multi-agent。**
