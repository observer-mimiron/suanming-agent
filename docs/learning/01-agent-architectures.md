# 主流 Agent 架构综述

**用途：** 帮助理解不同 Agent 架构适合解决什么问题，以及它们在本项目里有没有必要。

---

## 1. 单 Agent + Tools

### 定义

一个模型，外挂若干工具。模型根据用户输入决定是否调用工具，然后组织最终回复。

### 特点

- 最简单
- 最容易落地
- 调试成本最低
- 很适合单领域问题

### 优点

- 架构清晰
- 上手快
- 工程复杂度低

### 缺点

- 状态复杂时容易写散
- 条件边多时可维护性下降
- 工具增多后 prompt 容易膨胀

### 适用场景

- FAQ
- 单领域助手
- 工具数量不多的业务系统

### 本项目判断

**非常适合 v1 起步。**

---

## 2. ReAct

### 定义

模型以“思考 → 行动 → 观察”的小步循环推进任务。

### 特点

- 即时决定下一步
- 边想边调用工具
- 不需要先完整产出大计划

### 优点

- 灵活
- 对开放式问题效果不错
- 适合探索型任务

### 缺点

- 容易循环
- 难预测执行路径
- 调试难度比单次调用大

### 适用场景

- 搜索
- 调研
- 开放式问答

### 本项目判断

**可以理解，但不建议作为主线。**  
八字排盘流程相对确定，不需要大量自由探索。

---

## 3. Plan-Execute

### 定义

先生成一个计划，再按计划执行工具，最后汇总结果。

### 特点

- 比 ReAct 更稳定
- 路径更清晰
- 更适合可拆步骤的任务

### 优点

- 可观测性好
- 适合结构化业务流程
- 更容易做 UI 展示

### 缺点

- 计划可能一开始就错
- 计划变更成本高
- 对动态场景不如 ReAct 灵活

### 适用场景

- 表单式流程
- 数据处理流水线
- 业务步骤相对固定的系统

### 本项目判断

**很适合作为理解参考。**  
但 v1 用 Go 状态机就能覆盖主要收益，不一定非要显式做成 Planner。

---

## 4. State Machine / Workflow

### 定义

把系统显式拆成若干状态和状态转移，用确定性逻辑控制流程。

### 特点

- 最工程化
- 最可测
- 最适合业务流程

### 优点

- 条件边可控
- 易写测试
- 易解释

### 缺点

- 灵活性不如 ReAct
- 复杂后会变得啰嗦
- 状态设计不好时会难维护

### 适用场景

- 多轮信息收集
- 审批流
- 表单流
- 业务确定性强的 Agent

### 本项目判断

**这是 v1 的核心架构。**

---

## 5. Planner + Conditional Routing

### 定义

模型负责做结构化判断，系统根据判断走不同分支。

### 特点

- 介于纯状态机和自由 Agent 之间
- 保留一定智能判断
- 又不像开放式 loop 那么不可控

### 优点

- 比纯 if-else 更灵活
- 比 ReAct 更稳
- 适合有条件边的业务场景

### 缺点

- 仍然需要清晰的状态边界
- 模型判断错了会走错分支
- 双栈时协议设计会变复杂

### 适用场景

- 资料采集歧义处理
- 主题路由
- 多模式执行决策

### 本项目判断

**这是 LangGraph v2 最值得学习的点。**

---

## 6. Agent Loop

### 定义

Agent 不只运行一步，而是循环执行：

- 判断
- 调工具
- 观察结果
- 再决定下一步

### 两种形态

#### 6.1 Bounded Loop

有明确上限和退出条件。

优点：

- 可控
- 可测试
- 适合业务系统

#### 6.2 Open-ended Loop

没有很强的上限，模型自由决定是否继续。

优点：

- 灵活

缺点：

- 容易失控
- 容易烧 token
- 很难解释

### 本项目判断

- **值得学 bounded loop**
- **不建议做 open-ended loop**

---

## 7. Skill-based Architecture

### 定义

把能力打包成较稳定的技能单元。每个 skill 通常包含：

- 能力定义
- 输入输出约束
- 所需上下文
- 最佳实践

### 特点

- 适合能力复用
- 适合多领域扩展
- 比单纯工具更强调“能力包”

### 优点

- 模块化强
- 适合做长期演进
- 有利于不同任务复用

### 缺点

- 抽象成本高
- 过早设计容易空转
- 只有单领域时收益有限

### 适用场景

- 多能力平台
- 复杂产品线
- 有多个相对独立的 domain capability

### 本项目判断

**可以学思路，但不必在 v1 做重型 skill runtime。**

---

## 8. Manager / Supervisor Multi-Agent

### 定义

一个 manager 或 supervisor 负责把任务分派给多个 specialist agent。

### 特点

- 强调角色分工
- 强调上下文隔离
- 适合多领域复杂任务

### 优点

- 适合复杂系统拆分
- specialist 可以独立优化
- 角色边界清楚时效果很好

### 缺点

- prompt 和协议复杂
- 上下文协调难
- 很容易为拆而拆

### 适用场景

- 多领域平台
- 代码代理
- 需要多个独立 specialist 协作的场景

### 本项目判断

**当前没必要。**  
只有当产品扩到八字、六爻、姓名分析、专项咨询等多个独立域时，才开始有意义。

---

## 9. MCP-centric Architecture

### 定义

把外部能力和知识统一通过 MCP 暴露给 Agent 使用。

### 特点

- 工具接入标准化
- 知识和能力可以解耦
- 更接近真实生态集成

### 优点

- 扩展性好
- 更利于复用外部能力
- 适合长期演进

### 缺点

- 需要处理协议和失败降级
- 本地调试链路更长
- 不是所有项目都需要这么重

### 本项目判断

**非常值得学。**  
因为你已经有项目知识库 MCP / skill 知识库 MCP，这正好是一个真实的学习场景。

---

## 10. 推荐学习顺序

### 第一阶段

- 单 Agent + Tools
- State Machine
- MCP 集成

### 第二阶段

- Planner + Conditional Routing
- Bounded Loop
- LangGraph

### 第三阶段

- Skill-based architecture
- Manager / Supervisor
- Multi-Agent

---

## 11. 一句话判断

| 架构 | 值不值得学 | 现在要不要上项目主线 |
|------|------------|----------------------|
| 单 Agent + Tools | 值得 | 要 |
| State Machine | 值得 | 要 |
| MCP-centric | 值得 | 要 |
| Plan-Execute | 值得 | 可作为参考 |
| ReAct | 值得理解 | 不建议主线采用 |
| Planner + Routing | 值得 | 放 v2 |
| Bounded Loop | 值得 | 放 v2 |
| Open-ended Loop | 可了解 | 不建议 |
| Skill-based | 值得 | 放 v3 或轻量化吸收 |
| Manager / Multi-Agent | 值得 | 当前不需要 |
