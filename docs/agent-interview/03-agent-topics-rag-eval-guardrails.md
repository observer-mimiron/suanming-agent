# Agent 高频专题：RAG、Eval、Guardrails、Observability

结论：这一页不是给你“知道几个词”用的，而是给你把二面和深挖面里的高频追问讲透。重点只有一个：RAG 必须单独讲成主战场，因为大部分 Agent 面试最后都会回到检索质量、证据控制、评测闭环和工程稳定性。

## 1. 这一页到底要解决什么

你学完这一页，至少要能做到 4 件事：

1. 能把 RAG 从“接知识库”讲到 retrieval pipeline（检索流水线，指从 query 到证据入模的整条链）
2. 能把 eval 从“看回答好不好”讲到离线数据集、在线指标、坏例回流
3. 能把工程化问题讲清，比如并发、背压、幂等、队列、超时、可观测性
4. 能把 guardrails（程序保护栏，负责限制越界和错误扩散）讲成分层控制，而不是一句“最后加个兜底 prompt”

## 2. 先背住的大图

如果面试官问你“你怎么理解一个成熟的 Agent 系统”，你可以先给这张图：

`入口 -> route -> execution contract -> retrieval / tool use -> compose -> guard -> trace / eval`

如果他继续追问 RAG，你就切到这张图：

`query understanding -> rewrite -> retrieval -> fusion -> rerank -> grounding -> answer -> citation -> eval`

这两张图够你把多数问题接住。

## 3. RAG 为什么必须单独讲

### 3.1 短答

RAG 不是“给模型多塞一点资料”，而是“让回答建立在可追溯证据上，同时把成本、时延、失败降级和质量评测放进工程闭环”。

### 3.2 展开

很多人把 RAG 讲成两步：

1. 向量化
2. 检索后拼 prompt

这在面试里通常不够，因为真正高频追问是这些：

1. 什么时候触发检索
2. query 怎么改写
3. 召回为什么用混合检索
4. 召回后为什么还要 rerank（重排，指对召回结果二次排序）
5. 证据怎么入模，怎么限制幻觉
6. 没查到怎么办
7. 怎么证明这条 RAG 链真的提升了答案
8. 成本、时延和质量冲突时怎么取舍

### 3.3 如何落地

你可以把 RAG 直接讲成 8 个节点：

1. 触发检索
2. 理解 query
3. 重写 query
4. 多路召回
5. 融合排序
6. 二次重排
7. 证据成文
8. 评测闭环

### 3.4 面试误区

1. 只讲 embedding，不讲整条链
2. 只讲召回，不讲回答如何消费证据
3. 只讲命中率，不讲最终回答质量
4. 只讲“模型会自己判断”，不讲程序边界

## 4. 结合这个项目，RAG 应该怎么讲

### 4.1 短答

这个项目的检索不是“知识库直接替我回答”，而是“知识库负责返回证据，runtime 负责消费证据并生成最终答复”。

### 4.2 展开

你可以直接绑定仓库真实锚点：

1. 检索工具是 `knowledge_search`（知识检索工具，负责取回 passages）和 `knowledge_catalog`（知识目录工具，负责先看书目和章节）
2. 运行时主链是 `RouteAdvisor -> Policy Gate -> Manager -> ExecutionPlan -> Prefill -> specialist runner(s) -> manager compose -> final guard -> SSE`
3. 八字 authority-first graph（权威优先图，先证据后成文）里，检索结果会进入 `evidence bundle`（证据包，负责承接结构化证据）
4. 最终回答不是检索工具直接输出，而是 manager 和 renderer 消费结构化结果后成文
5. 项目已经明确做过 “0 命中不直接报废，继续保守成文” 的降级处理

### 4.3 如何落地

你可以这样讲项目里的边界：

> 在这个项目里，我把 RAG 边界切得比较清楚。知识库负责 retrieval，返回 passages；runtime 负责决定什么时候查、查几次、怎么消费证据、怎么做最终成文。这样好处是工具职责窄，输出边界清楚，也更容易做 trace 和 eval。

### 4.4 面试误区

1. 说成“知识库直接生成答案”
2. 不提 `0-hit` 降级
3. 不提 evidence bundle 和 citation 边界
4. 不提检索次数预算和来源边界

## 5. RAG 全链路怎么讲

## 5.1 面试官问：你设计一条 RAG pipeline，会怎么拆

### 短答

我会拆成：query understanding、query rewrite、multi-retrieval、fusion、rerank、grounding、citation、fallback、eval。

### 展开

一条成熟 RAG 链至少有下面这些层：

1. query understanding（问题理解，先识别真实信息需求）
2. query rewrite（问题改写，把口语问题改成适合检索的查询）
3. retrieval（召回，通常不只一种索引）
4. fusion（融合，把多路召回合并）
5. rerank（重排，把“像”变成“更相关”）
6. grounding（证据落地，让回答绑定证据）
7. citation（引用输出，让证据能回指）
8. fallback（降级策略，处理弱命中和 0 命中）
9. eval（评测，证明这条链真的有效）

### 如何落地

最稳的讲法不是抽象大词，而是按顺序说：

1. 先决定这轮要不要查
2. 再把原始问题改写成更可检索的 query
3. 然后用 BM25 + 向量 + 规则过滤做多路召回
4. 用 RRF（倒数排名融合，按名次融合多路结果）先做粗融合
5. 再用 rerank 模型做精排
6. 最后把证据片段和来源约束传给生成层

### 面试误区

1. 把“向量检索”当成 RAG 全部
2. 召回完直接拼上下文，不做融合和重排
3. 不讲 0-hit 和低质量证据怎么处理

## 5.2 面试官问：什么时候触发检索

### 短答

不是所有请求都该查。检索应该由信息缺口触发，而不是每轮默认都查。

### 展开

常见触发条件有 4 类：

1. 用户问题依赖外部知识或长尾资料
2. 当前上下文没有足够证据支撑回答
3. 这是强事实型问题，不能只靠模型先验
4. 需要引用原文、出处或可验证依据

不该查的场景也要会说：

1. 纯格式化改写
2. 通用常识解释且风险低
3. 当前 session 已有可复用 artifact（执行产物，指本轮或前轮已准备好的结构化结果）
4. 查了也不能提升正确性，只会增时延和成本

### 如何落地

在这个项目里，你可以对应到：

1. route 和 manager 先判断本轮任务意图
2. 如果是命理解读里的证据不足，再触发 controlled retrieval（受控检索，指有预算和边界的检索）
3. 如果是 follow-up 且已有可复用结果，优先复用，不必重新检索

### 面试误区

1. 逢问必查
2. 不区分“需要事实”和“只需表达”
3. 不把复用缓存结果算进检索策略

## 5.3 面试官问：query rewrite 有什么用

### 短答

用户语言经常不适合直接检索，query rewrite 的作用是把模糊、口语、冗长的问题改写成更可召回的查询表达。

### 展开

rewrite 常见作用有 5 类：

1. 去噪，把寒暄、背景话删掉
2. 补关键词，把隐含术语显式化
3. 结构化，把问题拆成主问题和过滤条件
4. 改写粒度，把“大而泛”的问题改成可查的小问题
5. 多 query 扩展，让一个问题生成多条检索表达

例如：

- 原问：`我这个盘为什么总是先顺后逆？`
- 改写后可能变成：
  - `八字 先顺后逆 命理 原因`
  - `大运 流年 吉中有阻 古籍`
  - `事业 运势 承托与限制并存 命理`

### 如何落地

你可以说两种实现方式：

| 方案 | 核心差异 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| 规则改写 | 用模板和词表改写 | 领域术语稳定 | 稳、便宜、可控 | 覆盖有限 |
| LLM 改写 | 让模型生成 1 到 N 条检索 query | 自然语言变化大 | 灵活、召回潜力高 | 成本更高，需约束 |

### 面试误区

1. 只说“为了提高召回”，但讲不出怎么改
2. 只生成很多 query，不做 budget 控制
3. 改写后不做去重和质量过滤

## 5.4 面试官问：chunking 怎么做

### 短答

chunking（分块，指把文档切成可索引片段）不是越小越好，也不是越大越好，关键是让“一个 chunk 能承载一个相对完整语义单元”。

### 展开

chunk 设计通常看 4 个因素：

1. 文档结构：标题、章节、表格、代码、段落
2. 检索粒度：用户通常问段级、页级还是章节级问题
3. 模型窗口：最终要放进 prompt 的证据容量
4. 引用需求：是否需要稳定定位来源

常见分块策略：

| 方案 | 核心差异 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| 固定长度分块 | 按字符或 token 切 | 快速起步 | 简单、统一 | 容易切断语义 |
| 结构化分块 | 按标题、段落、表格切 | 文档结构清楚 | 语义更完整 | 解析复杂 |
| 递归分块 | 先大后小逐级切 | 混合文档 | 兼顾结构和长度 | 参数更多 |
| 父子块 | 检索小块，回填大块 | 既要精度又要上下文 | 回答更完整 | 实现更复杂 |

### 如何落地

面试里最稳的回答是：

> 我不会一开始只调 chunk size。我会先看问题类型和文档结构，再决定切段策略。经验上，先保证标题、段落、表格边界不被破坏，再微调 chunk size、overlap 和 parent-child 回填，比单独盲调长度更有效。

### 面试误区

1. 把 chunking 理解成“切 500 token 就行”
2. 不谈 overlap（重叠区，负责降低切断语义风险）
3. 不谈表格、列表、代码块这些特殊结构

## 5.5 面试官问：为什么要做 hybrid search

### 短答

hybrid search（混合检索，指关键词检索和向量检索结合）是为了同时覆盖“精确术语匹配”和“语义相似匹配”。

### 展开

单一路径各有短板：

1. 纯 BM25（关键词检索，按词频和倒排召回）对专有名词、精确短语很好，但容易漏语义近义表达
2. 纯向量检索对语义相似更强，但容易把“看起来像”的内容拉上来，且对明确术语、数字、版本号不稳定

所以混合检索更常见，因为它能同时吃到：

1. 关键词精确性
2. 语义召回能力
3. 更稳的长尾覆盖

### 如何落地

你可以直接说：

> 如果文档里有很多专业术语、章节名、法条号、版本号、命理术语，我通常不会只上向量检索。更稳的方案是 BM25 和向量并行召回，再做融合和重排。

### 面试误区

1. 觉得有 embedding 就不需要 BM25
2. 只讲“效果更好”，不讲为什么
3. 不知道混合之后要怎么融合

## 5.6 面试官问：RRF 是什么，为什么常见

### 短答

RRF 是一种很实用的融合方法，它不依赖不同召回分数可直接比较，而是按各自排名来融合结果。

### 展开

多路召回最大的问题是分数体系不同：

1. BM25 分数和向量相似度不可直接比较
2. 不同索引、不同模型的分数尺度不统一

RRF 的好处就是：

1. 不强依赖原始分数
2. 工程实现简单
3. 对多路召回融合很稳

### 如何落地

最稳的说法是：

> 我一般先用 RRF 做第一层融合，因为它简单、鲁棒，不需要花太多精力做分数校准。等召回链稳定后，再决定要不要上更复杂的 learning to rank 或自定义融合。

### 面试误区

1. 说不清 RRF 解决什么问题
2. 以为融合就是把分数相加
3. 把 RRF 当成最终精排，而不是粗融合

## 5.7 面试官问：为什么还要 rerank

### 短答

因为召回的目标是“别漏”，重排的目标是“把最相关的放前面”。

### 展开

retrieval 和 rerank 的职责不同：

1. retrieval 追求 recall（召回率，尽量别漏）
2. rerank 追求 precision（精确性，让前几条更像正确答案）

你可以直接说 rerank 解决的 3 个问题：

1. 多路召回回来太杂
2. 真正有用的证据排得不够靠前
3. prompt 容量有限，必须先压缩成高价值证据

### 如何落地

常见顺序是：

1. BM25 和向量并行召回 topK
2. RRF 融合成候选集
3. 用 rerank 模型把 topN 排序
4. 只把最有价值的少量片段送给生成层

### 面试误区

1. 只讲召回，不讲精排
2. topK 拉很大，最后全塞 prompt
3. 不知道 rerank 的意义在于“压缩高价值上下文”

## 5.8 面试官问：grounding 和 citation 怎么做

### 短答

grounding（证据落地，指让回答只建立在证据和允许推断范围上）解决“话从哪来”；citation（引用回指，指把回答映射回原始证据来源）解决“证据在哪”。

### 展开

成熟系统至少要做 3 件事：

1. 限定回答只能引用提供的证据
2. 区分“直接证据”和“基于证据的推断”
3. 输出来源信息，让用户或评审可追溯

你可以这样区分：

1. grounding 是模型行为约束
2. citation 是用户可见回指
3. 两者一起才能降低“像真但不可证”的回答

### 如何落地

在这个项目里可以这样讲：

1. `knowledge_search` 返回 passages 和 source
2. `evidence bundle` 只承接真实检索到的证据
3. prompt 和 renderer 约束“没有引用就不要伪造出处”
4. 最终回答里可以保留“依据 / 引文 / 古籍来源”这类结构

### 面试误区

1. 只给模型看资料，不做出处回指
2. 模型自由发挥后再人工相信它
3. 没命中证据还硬造引用

## 5.9 面试官问：0-hit 怎么办

### 短答

0-hit 不是异常分支，而是 RAG 必须正面设计的正常分支。

### 展开

0-hit 常见原因有：

1. query 不好
2. chunk 不好
3. 索引覆盖不够
4. 过滤条件太严
5. 用户问的是知识库里根本没有的东西

成熟降级至少有 4 层：

1. retry rewrite：换 query 再试一次
2. broaden recall：放宽过滤或扩查询
3. answer with uncertainty：明确说明没找到直接证据
4. fallback mode：转成保守回答、澄清提问或拒答

### 如何落地

这个项目已经有一条很好的面试素材：

> authority-first 八字链已经修过 “0 命中不直接 agent_error，而是继续走静态/动态综合并保守成文”。这说明我们把 0-hit 当成受控降级，而不是系统崩溃。

### 面试误区

1. 0-hit 就返回系统错误
2. 0-hit 还硬编出处
3. 0-hit 不打 trace，后面没法排障

## 5.10 面试官问：RAG 调优顺序怎么排

### 短答

我的调优顺序通常不是先调 prompt，而是先把检索链本身调顺：问题定义 -> 数据切块 -> query -> 召回 -> 融合 -> 重排 -> 成文 -> 评测。

### 展开

更稳的顺序通常是：

1. 先定义任务和评测集
2. 先看有没有索引和分块问题
3. 再看 query rewrite
4. 再看召回通道是否单一
5. 再看 rerank 是否缺失
6. 再看 prompt 如何消费证据
7. 最后才是细调回答话术

因为很多团队一上来就调 prompt，结果真正问题其实是：

1. 没召回到
2. 召回太杂
3. 召回有了但没正确引用
4. 证据进入 prompt 的方式不对

### 如何落地

你可以背这个顺序：

1. 先查数据
2. 再查检索
3. 再查重排
4. 再查成文
5. 最后查 prompt

### 面试误区

1. 坏答案就先怪模型
2. 不做 retrieval ablation（消融对比，指逐段关闭组件验证贡献）
3. 没有离线集，纯靠主观试几遍

## 5.11 面试官问：RAG 的成本和时延怎么权衡

### 短答

RAG 本质是用检索成本换更稳的事实质量，但检索链本身也有预算，所以要分层控成本，而不是默认开满。

### 展开

主要成本来源有 5 类：

1. query rewrite 的 LLM 调用
2. 多路召回
3. rerank 模型
4. 大量上下文注入
5. 失败重试和多跳检索

时延控制常见做法：

1. rewrite 限次
2. 并行召回
3. RRF 粗融合后尽快截断
4. rerank 只对少量候选做
5. 引文只保留高价值片段，不把整页塞进去

### 如何落地

你可以这样说：

> 我的原则是把贵的步骤放在后面。先用便宜的召回扩大覆盖，再对少量候选做更贵的 rerank 和成文。这样通常比一开始就用大模型重写、多次多跳检索更稳。

### 面试误区

1. 只谈质量，不谈 latency
2. 只谈 latency，不谈回答可信度
3. 每条 query 都走最贵链路

## 5.12 面试官问：RAG 常见故障有哪些

### 短答

最常见的不是模型笨，而是证据链断裂。

### 展开

高频故障可以分 8 类：

1. 根本没触发检索
2. query rewrite 错了
3. chunk 切坏了
4. 只靠单路召回，漏了
5. 召回到了但排序不对
6. 证据入模太多，噪声压过主证
7. 成文阶段没守住引用边界
8. 没 trace，出了问题只能猜

### 如何落地

面试里你可以给一个排障顺序：

1. 看有没有命中检索
2. 看 query 是什么
3. 看召回列表
4. 看 rerank 前后变化
5. 看最终注入的证据片段
6. 看回答是否引用到了真实证据

### 面试误区

1. 出问题只看最后回答
2. 不看检索中间态
3. 不保留召回、融合、重排的调试信息

## 6. RAG 评测怎么讲

## 6.1 面试官问：RAG 怎么评测

### 短答

RAG 不能只评最终文案，要把检索链和生成链拆开评。

### 展开

至少拆成两层：

1. retrieval eval（检索评测，判断该查到的有没有查到）
2. answer eval（答案评测，判断回答是否正确、有据、不过界）

更细一点可以拆成 5 层：

1. 触发检索对不对
2. query rewrite 是否提升召回
3. topK 是否覆盖关键证据
4. citation 是否真实可回指
5. 最终回答是否正确且 grounded

### 如何落地

离线你可以做：

1. 题目
2. 标准证据
3. 标准答案或评分规则
4. 对比不同检索策略

在线你可以看：

1. 0-hit rate
2. citation 使用率
3. 用户追问率
4. 人工纠错率
5. retrieval latency

### 面试误区

1. 只用“感觉回答更好了”
2. 不分 retrieval 和 answer
3. 不留坏例回流机制

## 6.2 面试官问：离线评测和在线评测有什么差别

### 短答

离线评测解决“能不能稳定比较方案”，在线评测解决“真实流量下有没有副作用”。

### 展开

离线评测关注：

1. 可重复
2. 可对比
3. 可回归

在线评测关注：

1. 真实用户问题分布
2. 实际成本和时延
3. 回答是否减少追问和人工修正

### 如何落地

在这个项目里可以映射成：

1. `eval/datasets/*.json` 做最小离线样本
2. Langfuse 的 dataset run 和 score 承接对比
3. trace / session 承接真实线上路径观察

### 面试误区

1. 离线效果好就当线上一定好
2. 线上有数据却不回流离线集
3. 只看单轮回答，不看 follow-up

## 7. Eval 设计怎么讲

## 7.1 面试官问：Agent 系统的 eval 怎么设计

### 短答

我会把 eval 设计成“分层合同测试 + 数据集回归 + 线上观测”的三层结构，而不是只做最后答案打分。

### 展开

比较稳的三层是：

1. 合同测试：检查 route、artifact、guard、输出结构有没有破
2. 数据集回归：检查一组固定样本在不同版本下谁更好
3. 线上观测：看真实流量中的成本、时延、降级、失败类型

你也可以补一句：

> 如果是 Agent，不拆层就很容易误判。因为坏结果可能是 route 错、tool 错、retrieval 错、compose 错，不一定是模型本身错。

### 如何落地

这个项目里你可以这样讲：

1. Go 合同测试保证关键结构不乱
2. `eval/datasets/*.json` 做样本回归
3. Langfuse 负责 trace、session、dataset run、score
4. 本地 trace 和 debug 面板负责排障

### 面试误区

1. 只看一个总分
2. 不区分离线和在线
3. 不把坏例变成长期资产

## 7.2 面试官问：如果评测结果变差，你怎么排

### 短答

先定位是哪一层变差，再决定是回滚、修规则、修检索、还是修 prompt。

### 展开

排查顺序通常是：

1. route 是否漂了
2. 检索触发条件是否变了
3. query rewrite 是否异常
4. topK 质量是否下降
5. final guard 是否更常拦截
6. 成本和时延是否逼出了更多降级

### 如何落地

你可以给一个工程化答法：

> 我一般会先抽坏例看 trace，再对照 dataset run。因为只看最后总分，往往不知道是召回变差、重排变差，还是 guard 把原本能过的回答拦掉了。

### 面试误区

1. 一变差就只改 prompt
2. 不做版本对比
3. 不留执行路径证据

## 8. 并发、队列、背压、幂等怎么讲

## 8.1 面试官问：Agent 系统的并发问题主要在哪

### 短答

并发问题不只是“QPS 扛不扛得住”，更关键是 session 一致性、工具副作用、超时传播和资源争抢。

### 展开

高频并发风险有 5 类：

1. 同一个 session 被并发写坏
2. 同一个任务重复执行
3. 检索和工具调用把下游打爆
4. SSE 长连接占住资源
5. 一轮超时拖垮后续请求

### 如何落地

结合本项目可以这样讲：

1. `session_id` 让对话状态有归属
2. `ExecutionSnapshot`（执行快照，负责记录本轮正式执行合同）让你知道这轮到底做了什么
3. MemoryStore 并发隔离测试能说明团队已经意识到 session 并发安全问题

### 面试误区

1. 只谈线程池，不谈会话一致性
2. 只谈吞吐，不谈状态污染
3. 只谈模型慢，不谈下游工具也会被打爆

## 8.2 面试官问：什么是背压，为什么重要

### 短答

背压就是当下游处理不过来时，系统不能继续无限接单，而要主动限流、排队、降级或拒绝。

### 展开

Agent 系统特别容易出现隐性背压问题，因为一个用户请求可能扇出成：

1. 多次 LLM 调用
2. 多次检索
3. 多个工具调用
4. 长时间 SSE 输出

如果没有背压，后果通常是：

1. 队列堆积
2. 时延雪崩
3. 超时重试放大流量
4. 下游服务被拖垮

### 如何落地

你可以讲 4 种常见手段：

1. 并发上限
2. 队列长度上限
3. 超时和取消传播
4. 降级路径，比如关闭昂贵 rerank、减少 query rewrite 次数

### 面试误区

1. 把背压理解成只有消息队列才需要
2. 不做取消传播
3. 高峰期还让所有请求走最贵链路

## 8.3 面试官问：队列在 Agent 系统里什么时候该上

### 短答

不是所有 Agent 请求都该异步排队，但只要任务时间长、副作用重、可延后、且用户不需要秒回，就值得考虑队列化。

### 展开

适合队列的场景：

1. 批量 ingest（批量入库，指大量文档处理和索引写入）
2. 长时间评测任务
3. 异步知识刷新
4. 大规模离线 rerank 或重建索引

不适合全量队列化的场景：

1. 强交互聊天
2. 需要连续 SSE 反馈的会话
3. 需要即时澄清的多轮问答

### 如何落地

你可以这样回答：

> 我会把“在线会话”和“离线维护任务”拆开。会话主链偏同步和可取消；索引构建、批量数据处理、评测跑批更适合队列化。

### 面试误区

1. 一看到慢任务就全扔队列
2. 队列后没有可观测性
3. 不区分在线路径和后台任务

## 8.4 面试官问：幂等为什么重要

### 短答

幂等（同一请求重复执行，结果不应意外重复放大）是 Agent 工具安全和重试安全的基础。

### 展开

Agent 系统里重复执行很常见，因为会有：

1. 用户重复点击
2. 网络重试
3. 超时重放
4. worker 重启后续跑

如果没有幂等，可能出现：

1. 重复写库
2. 重复发通知
3. 重复扣费
4. 重复创建任务

### 如何落地

你可以给这套答法：

1. 高风险写工具必须带 request id
2. 服务端按幂等键去重
3. 对外部系统状态变更做结果缓存或状态检查
4. 非幂等工具默认不上自动重试

### 面试误区

1. 把幂等当成数据库问题
2. 只给读操作做重试
3. 不区分“可重试”和“可重放”

## 9. Observability 怎么讲

## 9.1 面试官问：为什么 Agent 系统更需要 observability

### 短答

因为 Agent 不是单次函数调用，而是一条多阶段、不完全确定、可能分叉和降级的执行链。没有 observability，你看到的只是一段最后回答，几乎没法排障。

### 展开

至少要回答 6 个问题：

1. 本轮走了哪条 route
2. 有没有触发 retrieval
3. retrieval 查了什么，返回了什么
4. 哪个环节最慢
5. 哪个 guard 或 fallback 命中了
6. 最终答案到底基于哪些 artifact 和证据

### 如何落地

在这个项目里，观测材料很足：

1. 本地 trace
2. SSE 的 `thinking / tool_call / component / text / done`
3. Langfuse 的 trace、session、dataset run、score
4. cheap gate 的本地样本和聚合报告

### 面试误区

1. 把 observability 等同于日志
2. 只保留最后答案，不保留中间态
3. 不追踪降级和 guard 命中

## 9.2 面试官问：你最关注哪些指标

### 短答

我一般把指标分成质量、效率、稳定性、控制边界 4 类。

### 展开

重点指标可以记这 12 个：

1. route 命中率
2. retrieval 触发率
3. 0-hit rate
4. rerank 命中贡献
5. citation 覆盖率
6. answer grounded rate
7. P50 / P95 latency
8. token cost
9. tool error rate
10. fallback / guard hit rate
11. session follow-up reuse rate
12. 人工纠错率或追问率

### 如何落地

最稳的答法是：

> 我不会只看一个总满意度分。对 Agent 来说，质量问题很多时候是链路问题，所以要把 route、retrieval、tool、guard、latency、cost 分开看。

### 面试误区

1. 只看响应时间
2. 只看 token cost
3. 只看最终答案评分

## 10. Guardrails 怎么讲

## 10.1 面试官问：guardrails 应该放哪几层

### 短答

guardrails 不能只放最后一层，成熟系统至少要有输入、route、tool、contract、输出五层。

### 展开

你可以直接背这 5 层：

1. 输入层：非法请求、缺资料、高风险意图识别
2. route 层：领域白名单、低置信度澄清、不可达路径拦截
3. tool 层：参数校验、权限、幂等、超时、结果过滤
4. contract 层：必须的 artifact 是否齐全
5. 输出层：脱敏、越界检查、内部细节屏蔽

### 如何落地

这个项目的映射很好讲：

| 层级 | 核心差异 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| `RouteAdvisor + Policy Gate` | 进执行前先控方向 | 路由、意图、资料判定 | 早发现、代价低 | 不能替代后续校验 |
| `ExecutionPlan + RequiredArtifacts` | 以合同控执行前置条件 | artifact 必备场景 | 可测、可审计 | 设计要清晰 |
| `Prefill / preflight` | 程序化硬判断 | 排盘、缺资料、短路澄清 | 稳、可控 | 灵活性有限 |
| `final guard` | 最终用户可见输出校验 | 脱敏、越界、合同兜底 | 最后收口 | 不该承担全部控制责任 |

### 面试误区

1. 只说“我加了一个最后兜底 prompt”
2. 不区分工具层和输出层
3. 不把 guard 命中纳入 trace 和 eval

## 10.2 面试官问：为什么 final guard 不够

### 短答

因为 final guard 只适合做最后一道验收，不适合替代前面的路径控制、artifact 校验和工具安全。

### 展开

如果把所有风险都留到最后：

1. 成本已经花掉了
2. 坏工具可能已经执行了
3. 用户体验已经变差了
4. 出问题更难定位

### 如何落地

你可以这样答：

> 我把 final guard 当成最后一道收口，不当成万能补丁。真正稳定的系统应该把控制前移，越早拦越便宜，越早拦越可解释。

### 面试误区

1. 把所有控制责任压给最后一步
2. 只靠提示词说“不要泄露”
3. 没有结构化合同和必备产物校验

## 11. 高频工程化追问

## 11.1 面试官问：Workflow 和 Agent 的边界是什么

### 短答

Workflow 负责稳定骨架，Agent 负责不确定环节；成熟系统通常不是二选一，而是 workflow 外壳里嵌 agent 节点。

### 展开

如果任务路径稳定、风险高、审计强，就更偏 workflow。  
如果理解需求、query rewrite、证据判断、总结表达有不确定性，就更适合用模型。

### 如何落地

这个项目就是典型例子：

1. route、artifact、guard、SSE 属于程序骨架
2. 检索规划、领域分析、成文解释属于模型参与区

### 面试误区

1. 觉得“用了 LLM 就是 Agent”
2. 不区分确定性步骤和非确定性步骤

## 11.2 面试官问：manager-worker 比 handoff 更适合什么

### 短答

当你需要统一对话 owner、统一体验、统一收口时，manager-worker 往往比 handoff 更稳。

### 展开

manager-worker 适合：

1. 多领域
2. 多工具
3. 多轮 follow-up
4. 最终回答必须统一口径

handoff 更适合：

1. 明确接力
2. 边界非常清楚
3. 不太需要统一 owner

### 如何落地

这个仓库的面试说法就很稳：

> 我们当前明确坚持 manager-owned runtime，因为 manager 是唯一 conversation owner，specialist 只做 bounded execution，不直接拥有最终用户答复权。

### 面试误区

1. 只说“多 Agent 更高级”
2. 不讲 owner 边界
3. 不讲 follow-up 下上下文谁负责

## 12. 这页最后要背住的 20 句

1. RAG 的重点是证据控制，不是把知识库接上。
2. 检索链至少要讲到 query rewrite、fusion、rerank、grounding、citation。
3. 0-hit 是正常分支，不是异常分支。
4. hybrid search 通常比纯向量更稳。
5. RRF 适合做多路召回的粗融合。
6. rerank 不是可有可无，它负责把有限 prompt 容量留给高价值证据。
7. 先调数据和检索，再调 prompt。
8. RAG 评测要拆 retrieval 和 answer 两层。
9. 离线评测解决可比较，在线评测解决真实性。
10. Agent eval 不该只看最终文案。
11. 并发问题核心不是线程数，而是 session 一致性和副作用控制。
12. 背压是为了防止下游被无限扇出打爆。
13. 队列适合长任务和后台任务，不适合所有强交互链路。
14. 幂等是重试安全的前提。
15. observability 不是日志堆积，而是还原真实执行路径。
16. trace 里必须看得到 route、retrieval、tool、guard、fallback。
17. guardrails 应该前移，不能只靠 final guard。
18. contract 比自由发挥更适合高风险执行链。
19. owner 边界比“有几个 agent”更重要。
20. 真正的 Agent 工程能力，不是会调模型，而是能把不确定性装进可控系统。
