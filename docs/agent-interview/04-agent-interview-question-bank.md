# Agent 面试强化题库与答案

结论：这份题库现在不再只是“够用版”，而是按一面、二面、部分 system design 深挖来写的强化版。

## 1. 使用方法

- 每题按 `短答 -> 展开 -> 项目映射 -> 常见追问` 背
- 一面重点背 `短答 + 项目映射`
- 二面重点背 `展开 + 常见追问`
- system design 题不要背定义，要把答案落回 `suanming-agent`

## 2. 必读答题原则

### 1. 面试里怎么判断“该讲概念”还是“该讲系统”

短答：

> 面试官先问定义，我会先给概念边界；一旦追问怎么落地，我就切到系统结构、失败模式和权衡。

展开：

- 定义题先回答“它是什么，不是什么”
- 工程题再回答“为什么这样设计，没这样做会出什么问题”
- 面试里最危险的是全程讲抽象名词，不讲控制面和失败面

项目映射：

- 在这个项目里，我不会只说“我们做了 multi-agent”
- 我会直接讲当前稳定主链：`RouteAdvisor -> Policy Gate -> Manager -> ExecutionPlan（执行合同对象） -> Prefill（确定性预填充） -> specialist runner(s)（限域执行器） -> manager compose -> final guard -> SSE`

常见追问：

- 你怎么证明这不是 PPT 架构
- 你怎么验证每一层真的起作用

### 2. 面试里怎么避免把 Agent 项目讲成“套壳调用模型”

短答：

> 不靠堆框架名，而是讲清 owner、状态、工具、检索、评测、观测和降级链。

展开：

- 只讲“用了什么模型”很弱
- 强一点的讲法是“模型在哪些点做决定，哪些点不让模型做决定”
- 再强一点是“当 route 错、retrieval 0 命中、artifact 缺失、follow-up 追问时，系统怎么保守降级”

项目映射：

- 这个项目不是“聊天 + prompt”
- 它有 route approval、execution contract、artifact prefill、bounded specialist、final guard、trace、regression dataset

常见追问：

- 你这个项目最像哪一类 Agent 系统
- 如果不让你讲模型，只讲系统，你怎么讲

## 3. Agent 基础题

### 3. 什么是 Agent

短答：

> Agent 是会在运行时根据上下文决定下一步动作的系统，不只是生成文本，还会决定是否调用工具、是否继续执行、是否结束。

展开：

- 普通 LLM 应用常常是一问一答
- Agent 更强调 loop、decision、tool use、state transition
- 真正的关键不是“会不会调工具”，而是“谁拥有流程控制权”

项目映射：

- 这个项目里，流程控制权不在 specialist，而在 `Manager`（运行时唯一会话 owner）

常见追问：

- chatbot 算不算 agent
- workflow 算不算 agent

### 4. Agent 和普通 chatbot 的区别

短答：

> chatbot 主要生成回复，agent 主要驱动执行。

展开：

- chatbot 的主问题是回复质量
- agent 的主问题是决策质量、执行稳定性和边界控制
- agent 会遇到 route 错误、工具失败、状态污染、检索漂移、长链路超时这些 chatbot 不明显的问题

项目映射：

- 这个项目不仅生成回答，还要决定领域、准备命盘、决定 follow-up 复用方式、做受控检索和最终 guard

常见追问：

- 什么时候 chatbot 就够了
- 什么时候一定要上 agent

### 5. 什么业务不适合 Agent

短答：

> 规则固定、路径稳定、错误代价高、确定性服务已足够的业务，不适合强行上 Agent。

展开：

- 纯 CRUD、纯查询、固定审批流，通常 workflow 就够
- 如果主要难点在权限、事务、一致性，不在推理，Agent 不会是主解
- Agent 值得上场的前提是存在复杂判断、非结构化输入、可控试错空间

项目映射：

- 命理解读这种任务包含自然语言理解、领域检索、追问承接、解释生成，更适合 agent than pure rules

常见追问：

- 哪些项目被你判断成不该做 agent
- 你怎么跟业务方解释“别上 agent”

### 6. workflow 和 agent 的边界是什么

短答：

> workflow 的路径主要由代码决定，agent 的下一步由模型参与决定。

展开：

- workflow 更强调确定性编排
- agent 更强调在多个可行路径里动态决策
- 生产里最稳的做法通常不是二选一，而是 workflow 外壳里放少量 agent 决策点

项目映射：

- 这个项目的 `orchestrationGraph`（运行时编排图）是 workflow 外壳
- route、follow-up policy、specialist 执行和最终 compose 中有 agent 决策点

常见追问：

- 如果要降风险，你先砍哪块 agent 自由度
- 你这个项目哪些部分更偏 workflow

### 7. 什么时候值得做多 Agent

短答：

> 当单 agent 的 prompt、工具集和领域边界已经不可维护时，多 Agent 才值。

展开：

- 多 Agent 不是为了显得高级
- 真正信号是：指令冲突严重、工具太多且相似、领域知识差异大、结果需要统一收口
- 如果单 agent 还能稳定工作，优先保留单 owner 结构

项目映射：

- 这个项目采用 manager-worker 思路，但不会让多个 specialist 都直接对用户说话

常见追问：

- 为什么不是每个领域一个自主 agent
- 什么时候多 Agent 会拖慢系统

### 8. handoff 和 manager-worker 的区别

短答：

> handoff 是执行权转移，manager-worker 是主控统一调度后再收口。

展开：

- handoff 像接力，后续 owner 可能变化
- manager-worker 像经理带团队，owner 一直在 manager
- 如果用户体验要求单一责任人，manager-worker 通常更稳

项目映射：

- 这个项目强调 `Manager` 是唯一 conversation owner，所以更接近 manager-worker

常见追问：

- handoff 的优点是什么
- manager-worker 最大缺点是什么

## 4. 架构与模式题

### 9. routing、workflow、manager-worker 怎么选

短答：

> 请求差异大先 routing；步骤固定先 workflow；多子任务且最终需要统一 owner 时选 manager-worker。

展开：

- routing 解决“去哪里”
- workflow 解决“怎么按固定步骤走”
- manager-worker 解决“多个能力协同时谁最终负责”

项目映射：

- 这个项目三者都有，但 owner 落在 manager，route 不直接等于执行

常见追问：

- 哪层最容易做过度设计
- 你最想删掉哪层复杂度

### 10. 为什么很多系统不该一开始就做 fully autonomous agent

短答：

> 因为自由度越高，评测、回归、排障和成本控制越难。

展开：

- 早期最重要的是验证价值，不是追求自主性
- 全自主系统最容易把失败原因藏起来
- 先做可控主链，再逐步增加模型决策点，工程上更稳

项目映射：

- 这个项目一直在收口到 manager-owned runtime，而不是继续放大 specialist 自由度

常见追问：

- fully autonomous 什么时候值得尝试
- 你如何逐步放权

### 11. 你怎么看“Agent 就是 prompt engineering”

短答：

> prompt 很重要，但生产 Agent 是系统工程，不只是 prompt 工程。

展开：

- prompt 只覆盖模型行为的一部分
- 真正决定上线质量的还有工具边界、状态机、合同、观测、评测和 guardrails
- prompt 写得再好，也解决不了并发串状态和外部依赖不稳定

项目映射：

- 这个项目后期的重点不是继续改大 prompt，而是收口 `ExecutionPlan`、`ExecutionSnapshot`（执行快照）和 cheap gate

常见追问：

- 那 prompt 优化还有没有价值
- 什么问题不该继续靠 prompt 修

### 12. 为什么 owner 边界重要

短答：

> 因为只要 owner 不清楚，多轮追问、跨域综合和失败收口都会漂。

展开：

- owner 负责上下文承接
- owner 负责最后对用户负责
- owner 负责在多个局部结果之间做统一解释

项目映射：

- 这个项目明确让 `Manager` 持有 owner，而不是让 bazi / qimen / ziwei specialist 各自收口

常见追问：

- owner 交给 route 行不行
- owner 和 orchestrator 的区别是什么

### 13. route 不等于 execution contract，为什么

短答：

> route 只解决理解，execution contract 解决真实执行要求。

展开：

- route 回答的是主领域、任务意图、槽位
- execution contract 还要补 domains、required artifacts、follow-up mode、直接答还是重跑
- 如果把两者混在一起，执行层会偷偷再做判断，系统会失控

项目映射：

- 这个项目把 `ApprovedRoute`（批准后的路由）和 `ExecutionPlan` 分开，就是为了防止执行层继续隐式路由

常见追问：

- execution contract 应该长什么样
- contract 怎么帮助评测

### 14. 为什么要把 artifact 思维放进 Agent 系统

短答：

> 因为很多回答依赖中间产物，没有 artifact，系统就只能靠模型现编。

展开：

- artifact 是结构化、可验证、可复用的中间结果
- artifact 把“推理前置”和“自由生成”分开
- 它还能支撑 follow-up 复用，降低重复执行

项目映射：

- 这个项目会先 prefill 命盘，再交给领域执行，follow-up 也优先复用已有解读资产

常见追问：

- artifact 和 cache 的区别是什么
- 哪些中间结果不值得做 artifact

## 5. Tool 与执行控制题

### 15. tool 设计最重要的原则是什么

短答：

> 工具边界窄、参数结构化、返回值可消费、高风险操作可控。

展开：

- 窄边界能降低误用概率
- 结构化参数便于校验和回归
- 返回值要稳定，不能每次都像自由文本
- 高风险工具要有权限、幂等和审计

项目映射：

- 这个项目里的 `knowledge_search`（知识检索工具）只做证据召回，不负责最终解释

常见追问：

- 你怎么给工具写 schema
- 工具返回自然语言行不行

### 16. 你怎么防止模型乱调工具

短答：

> 限工具集合、限参数模式、做程序校验、必要时把高风险动作收回确定性服务。

展开：

- 模型不该看到与当前任务无关的大工具箱
- 参数要可验证，不能让模型自由拼字符串执行
- 对外部副作用要有 allowlist 和审计

项目映射：

- 这个项目的 specialist 是 bounded worker，不会被放成无边界 autonomous tool user

常见追问：

- 只靠 prompt 限制够不够
- 工具校验失败后怎么处理

### 17. 什么时候不该让 LLM 直接做最终执行

短答：

> 涉及资金、审批、权限、不可逆写操作时，不该只靠 LLM 决定。

展开：

- 这些动作要么需要确定性规则
- 要么需要人审
- 要么需要双重确认与审计日志

项目映射：

- 这个项目主要是解读系统，写操作风险不高，但仍然通过 final guard 限制越界输出和内部信息泄漏

常见追问：

- 什么叫不可逆动作
- human in the loop 放在哪层

### 18. 你怎么看 structured output

短答：

> structured output 是把模型输出变成程序合同的关键手段。

展开：

- 没有结构化输出，后续状态承接和评测会很弱
- 结构化输出可以让 route、tool result、analysis nodes 进入程序校验
- 它不保证全对，但能显著降低不可控性

项目映射：

- 这个项目后期一直在把 follow-up mode、topic mode、artifact requirement 前移到结构化字段里

常见追问：

- 结构化输出会不会牺牲表达力
- schema 变更怎么做兼容

### 18.1. 腾讯 AI 三面那类“工具调用链路治理”题怎么答

短答：

> 这类题不考“会不会调工具”，而是考你能不能把工具调用做成可控、可观测、可回放的执行链。

展开：

- 工具选择前先做意图识别、实体抽取、权限判断、会话态判断和工具健康度裁剪，别把全量工具直接扔给模型
- 工具 schema 要清晰表达参数约束和版本边界，避免模型自由拼字符串
- 缺参要分三类处理：可推断的结构化补全，不确定的追问，高风险参数不猜
- 工具失败要分层处理：超时、限流这类 transient error 可以重试；参数错回到补参节点；权限失败和业务拒绝禁止重试
- 有副作用的工具必须做幂等键、服务端去重和结果可查，不能把重复执行风险压给 Agent
- 长文本返回要先给摘要和关键字段，完整内容落对象存储，用 ID 追查
- 每次调用都要记工具名、版本、参数摘要、耗时、错误码、选择依据和 trace，方便复盘误调和链路追责
- schema 升级要做版本化，老会话走旧版，新会话灰度新版本
- 多工具依赖不要靠模型隐式保证顺序，应该由状态机或 DAG（有向无环图）编排
- 出现错误工具导致脏数据时，先止损冻结后续链路，再用同版本模型、schema、权限上下文回放，最后定位是描述、路由还是审批策略的问题

项目映射：

- 这个项目里可以把 `RouteAdvisor`、`Policy Gate`、`ExecutionPlan`、`final guard`、trace / eval 体系串起来讲，核心是“模型参与决策，但不放弃程序控制”
- 如果面试官继续追问，你就把重点落到三件事：工具边界、异常治理、和副作用控制

常见追问：

- 你怎么判断一个工具该不该给模型看
- 缺参补全和追问的边界怎么定
- 为什么重试不能一把梭
- 幂等键应该由谁生成
- 工具链路怎么做回放和复盘

### 19. 你怎么设计 agent loop 的退出条件

短答：

> 正常完成、工具失败、命中 guard、达到步数上限、拿到明确结构化结果，都是退出条件。

展开：

- 没有退出条件的 loop 很危险
- 步数上限是成本和稳定性的基础保护
- 工具连续失败时要中止而不是无限重试

项目映射：

- 这个项目很多路径不是无限 loop，而是 `preflight -> prefill -> specialist -> compose -> guard` 的有界主链

常见追问：

- 你如何设置 max turns
- 退出后如何给用户解释

### 20. 你怎么理解 bounded specialist

短答：

> 它是受限能力执行器，不拥有全局 owner，也不应该无限调用一切工具。

展开：

- bounded 是在能力、上下文、工具、输出责任上都有限
- 这样可以把错误范围锁在局部
- 也便于 manager 汇总结果和做最终 guard

项目映射：

- 这个项目里 bazi / qimen / ziwei specialist 都是 bounded runner，而不是自主主控 agent

常见追问：

- bounded 和 sandbox 有什么关系
- 如果 specialist 很强，为什么不直接让它回复用户

## 6. 状态、上下文、记忆题

### 21. state、memory、context 的区别

短答：

> state 是当前运行态，memory 是可跨轮复用的信息，context 是这一轮模型真正看到的输入。

展开：

- state 更偏程序对象
- memory 更偏长期沉淀
- context 是喂给模型的工作窗口

项目映射：

- 这个项目会把 `ExecutionSnapshot` 持久化到 session state，用于前端恢复和 follow-up 复用

常见追问：

- 什么信息适合做 memory
- 什么信息只该留在 state

### 22. 为什么不能把所有历史都塞进上下文

短答：

> 因为上下文是有限资源，全塞进去会提高成本、降低判别力，还会污染当前任务。

展开：

- 长上下文不等于高质量上下文
- 无关历史会干扰 route 和 tool choice
- 真正重要的是选取，而不是堆积

项目映射：

- 这个项目在 follow-up 上优先复用执行合同和解读资产，而不是简单拼接所有历史消息

常见追问：

- 长上下文模型是不是就能解决这个问题
- 你如何做上下文选择

### 23. follow-up 为什么难

短答：

> 因为它要同时判断复用什么、重跑什么、当前问题是否仍在同一任务语境里。

展开：

- follow-up 不只是把聊天历史带上
- 它还涉及 owner 延续、artifact 复用和风险判断
- 很多系统首轮能跑通，追问一来就乱

项目映射：

- 这个项目专门做了 cheap gate 和 follow-up policy，把普通追问与必须重跑的追问分开

常见追问：

- 你怎么判断普通追问
- 什么追问必须重跑

### 24. cheap gate 的价值是什么

短答：

> 它能让低风险 follow-up 复用已有执行合同，减少不必要的完整路由。

展开：

- 不是每轮都值得重跑 supervisor
- 追问里很多只是术语解释、展开说明、补充理由
- 把这类请求筛出来，可以明显降低时延和成本

项目映射：

- 这个项目把 cheap gate 放在 `backend/internal/supervisor/cheap_gate.go`
- 命中时会记录 `decision_source / gate_reason / reuse_cached_result`

常见追问：

- cheap gate 会不会误判
- 你怎么监控它的收益和副作用

### 25. `ExecutionSnapshot` 有什么价值

短答：

> 它让执行真相可恢复、可观测、可调试，而不是只剩最后一句回答。

展开：

- 没有执行快照，你很难知道上一轮到底跑了什么
- 有快照后，前端、trace、report 都能还原更真实的过程
- 它还是后续 cheap gate 和 follow-up 复用的基础

项目映射：

- 这个项目已把 `ExecutionSnapshot` 接到 session 恢复、process/debug 面板和 trace 投影里

常见追问：

- snapshot 应该记录哪些字段
- 会不会记录太多导致状态膨胀

### 26. memory 系统什么时候值得做

短答：

> 当存在明确跨轮价值，比如用户偏好、长期事实、跨会话延续时，memory 才值得做。

展开：

- memory 不是万能缓存
- 写入条件、过期策略、可验证性都很重要
- 很多团队做 memory 太早，最后得到的是污染而不是增益

项目映射：

- 这个项目当前更重视 session state 和 follow-up 资产复用，还没有把“长期记忆”做成主能力

常见追问：

- 你如何避免错误记忆被长期保留
- memory 和 RAG 的边界是什么

## 7. RAG 基础题

### 27. RAG 是什么

短答：

> RAG 是先检索外部知识，再把证据引入回答链路的方案。

展开：

- 它的核心价值是引入新鲜、可追溯、领域化证据
- 它不能自动解决推理、结构化生成和安全边界问题
- 检索质量和证据消费质量同样重要

项目映射：

- 这个项目的知识库服务跑在 `:3100`，后端通过 MCP 和 HTTP 薄入口做命理资料检索

常见追问：

- RAG 和搜索增强有什么区别
- RAG 一定比微调好吗

### 28. 你的 RAG 和普通“搜一把塞上下文”有什么区别

短答：

> 我更强调 controlled RAG，不是搜完直接拼，而是限制入口、次数、证据形态和消费方式。

展开：

- 普通拼接式 RAG 容易把系统变成黑盒
- controlled RAG 关注什么时候查、查什么、查几次、怎么引用
- 证据要可追踪，不能只有模型自己知道看了什么

项目映射：

- 这个项目把 `knowledge_search` 限定为证据召回，不让知识库直接生成最终命理解读

常见追问：

- controlled RAG 会不会降低召回率
- 证据引用怎么做

### 29. agentic RAG 是什么

短答：

> agentic RAG 是让模型参与决定何时检索、是否追加检索以及证据是否足够。

展开：

- 它比固定一步检索更灵活
- 但如果没有次数上限和来源约束，容易成本失控
- 最好让模型拥有“是否查”的自由，而不是“无限查”的自由

项目映射：

- 这个项目的八字 authority-first 链路会做受控检索，但不是让模型无上限地自由搜索

常见追问：

- agentic RAG 和传统两段式 RAG 怎么选
- 如何防止 agentic RAG 过搜

### 30. retrieval 0 命中怎么办

短答：

> 0 命中要进入 trace，但不一定整轮失败；关键是保守降级，不装作有证据。

展开：

- 0 命中首先要能被观测到
- 其次要区分“无证据可查”和“系统检索失败”
- 最后要决定是否继续走无证据保守回答，还是要求补信息

项目映射：

- 这个项目已把“检索 0 命中但继续保守成文”做成稳定路径，不再直接报阻塞性错误

常见追问：

- 什么场景 0 命中还能继续答
- 什么场景必须终止

### 31. 你怎么判断 retrieval 真的帮助了回答

短答：

> 不是看有没有调用工具，而是看证据是否相关、是否被消费、是否改善最终质量。

展开：

- 可以看引用覆盖率
- 可以看答案里是否真的落到了召回证据
- 还可以看有无证据时的质量差异

项目映射：

- 这个项目会看 retrieval quote case，不只看 `/api/chat` 能否跑完

常见追问：

- 你怎么做有无检索的 A/B
- 证据消费怎么评估

### 32. RAG 和 fine-tuning 怎么选

短答：

> 知识常变、需要引用来源时优先 RAG；行为稳定性和格式习惯问题再考虑微调。

展开：

- RAG 解决知识更新和可追溯
- 微调更适合风格、格式和行为偏好
- 很多时候是 RAG + prompt / tool 先走通，微调后补

项目映射：

- 这个项目的命理资料来自本地知识库，更适合 RAG，不适合把古籍知识直接固化进模型

常见追问：

- 什么情况下 RAG 不够
- 微调会不会掩盖知识错误

### 33. 你怎么控制检索失控

短答：

> 限入口、限 query 形状、限次数、限来源、限消费链路。

展开：

- 入口太多会让模型乱选
- query 太自由会让检索稳定性下降
- 次数不设上限会拉高时延和成本
- 来源不做约束会把不可信内容带进来

项目映射：

- 这个项目对知识检索有工具层边界和调用次数边界，不把 `query_wiki` 一类生成式问答直接放进 runtime 主链

常见追问：

- 你怎么设计 max retrieval count
- 查询改写由谁做

## 8. RAG 调优高频题

### 34. RAG 调优你先看召回还是先看答案

短答：

> 先拆开看召回和消费，不把“答案不好”一股脑归因给召回。

展开：

- 先看召回是否把对的证据带回来了
- 再看模型是否正确消费了证据
- 很多问题不是 recall 不够，而是 evidence synthesis 做坏了

项目映射：

- 这个项目如果回答偏了，我会区分 `knowledge_search` 没拿到证据，还是 graph / renderer 没把证据消费好

常见追问：

- 你如何定义“对的证据”
- 召回对了但答案还错怎么办

### 35. chunk 该怎么切

短答：

> 以语义完整和引用可读为先，不要只按固定 token 硬切。

展开：

- chunk 太小会丢上下文
- chunk 太大又会带太多噪音
- 最好围绕自然段、章节、条文或知识单元切

项目映射：

- 这个项目的知识库有古籍章节和目录页结构，天然适合按知识单元切，而不是只按字数切

常见追问：

- overlap 要不要加
- 图结构和 chunk 有什么关系

### 36. top-k 怎么调

短答：

> 先从能覆盖核心证据的最小 top-k 起步，再用数据看收益和噪音平衡。

展开：

- top-k 太小可能漏证据
- top-k 太大会引入噪音和时延
- 合理方法是结合 dataset 看命中率和最终质量曲线

项目映射：

- 这个项目更重“少量可信命中”，不是一口气塞很多古籍片段

常见追问：

- top-k 是否应按 query 类型动态调整
- top-k 和 rerank 的关系是什么

### 37. query rewrite 什么时候有用

短答：

> 当用户问法口语化、模糊或带代词时，query rewrite 很有用。

展开：

- rewrite 可以把自然语言转成更检索友好的表达
- 但改写本身也可能引入偏差
- 所以最好把 rewrite 结果可观测化，而不是默默改

项目映射：

- 这个项目如果以后继续优化检索，适合对“命理术语口语化表达”做轻量 rewrite，而不是完全自由改写

常见追问：

- rewrite 用规则还是模型
- 怎么评估 rewrite 是增益还是伤害

### 38. 混合检索为什么常见

短答：

> 因为关键词匹配和向量检索各有盲区，混合检索能提高稳健性。

展开：

- BM25 擅长字面匹配和专有名词
- 向量检索擅长语义近似
- 混合检索再配合 rerank，通常更适合生产

项目映射：

- 这个项目知识库已经有 BM25 + 向量 + RRF 混合召回思路，说明重点不是单一路径押宝

常见追问：

- RRF 是干嘛的
- 什么时候纯 BM25 更好

### 39. rerank 值不值得加

短答：

> 当初召回结果够多但排序不稳时，rerank 很值；如果召回本身就错了，rerank 救不了根因。

展开：

- rerank 主要解决“候选里有对答案，但排序不靠前”
- 它会增加时延和成本
- 适合证据质量要求高的场景

项目映射：

- 这个项目更看重最终引用质量，理论上适合在关键 retrieval path 上做轻量 rerank，而不是对所有查询一刀切

常见追问：

- rerank 放在线上还是离线
- 小模型 rerank 够不够

### 40. 你怎么处理多跳检索

短答：

> 先拆子问题，再做有限步检索，不让模型无限跳。

展开：

- 多跳问题常常不是一次 query 能解决
- 但多跳越多，漂移和成本越高
- 所以要限制 hop 数，并保留中间证据链

项目映射：

- 这个项目的古籍和命理解释有时会涉及“基础概念 -> 具体格局 -> 当前问题”的多跳关系，适合受控多步，而不是开放式浏览

常见追问：

- 多跳怎么评测
- hop 数如何设置

### 41. RAG 最常见的 5 类失败是什么

短答：

> 没召回、召回错、召回对但没消费、证据冲突没处理、证据和最终答案脱钩。

展开：

- failure taxonomy 很重要
- 没有分类，你就只能笼统说“RAG 不稳定”
- 分类后才知道该调索引、调 query、调 prompt 还是调 synthesis

项目映射：

- 这个项目的坏例分析就应该按 route / retrieval / final answer 分层，而不是一锅端

常见追问：

- 哪类失败最难修
- 你怎么做错误归因

### 42. RAG 评测要看哪些指标

短答：

> 至少看召回命中、证据相关性、引用覆盖、最终答案正确性、时延和成本。

展开：

- 只看最终文案不够
- 只看 recall 也不够
- RAG 是召回链和消费链共同决定的

项目映射：

- 这个项目的 retrieval quote case 就体现了“答案正确之外，还要看证据有没有真的进最终回答”

常见追问：

- 哪个指标最先做
- 人工评审怎么设计

## 9. Eval 与 Observability 题

### 43. 你怎么评估一个 Agent 系统

短答：

> 分层评估 route、tool、retrieval、artifact、final answer、latency、cost，而不是只看回答顺不顺眼。

展开：

- Agent 是链路系统，不是单点模型
- 最终答案对，不代表 route 对
- 最终答案错，也不一定是模型差，可能是检索或状态错

项目映射：

- 这个项目正式 truth layer 是 `Go 合同测试 + eval 数据集 + trace / session / dataset run / score`

常见追问：

- 你怎么设计最小可用 eval
- 一开始没数据怎么办

### 44. 为什么只看 UI 不够

短答：

> UI 只能看到表面结果，看不到系统到底怎么走到这个结果。

展开：

- UI 看不到 route 是否漂了
- 看不到工具有没有误调
- 看不到 retrieval 是否根本没贡献
- 也看不到 fallback 是否频繁触发

项目映射：

- 这个项目强调 trace、session、debug 面板，是因为只看最终聊天气泡根本不够

常见追问：

- 你上线后最常看哪个面板
- UI 和 trace 冲突时信哪个

### 45. trace 最重要的价值是什么

短答：

> trace 能还原真实执行链，让系统从黑盒变成可定位的问题链。

展开：

- trace 是排障工具
- 也是坏例回放工具
- 还是 prompt / route / retrieval 优化的数据来源

项目映射：

- 这个项目接了本地 trace 和 Langfuse，能看 session、dataset run、score，不只是原始日志

常见追问：

- trace 里最该打哪些事件
- trace 太多会不会影响性能

### 46. 你最关注哪些指标

短答：

> route 命中、tool 错误率、retrieval 0 命中、fallback 命中、artifact 缺失率、latency、cost。

展开：

- 指标要覆盖理解、执行、证据、成本和稳定性
- 如果只盯 token cost，很容易把关键质量问题漏掉
- 如果只盯 answer quality，又容易忽略系统退化

项目映射：

- 这个项目还专门沉淀了 cheap gate 命中样本和 summary，说明不是只看最终回答

常见追问：

- 哪个指标最容易被误读
- 线上指标和离线指标怎么配

### 47. Langfuse 在你项目里是干嘛的

短答：

> 它是观测和评测闭环的一部分，用来看 trace、session、dataset run、score 和坏例聚合。

展开：

- 它不只是日志面板
- 价值在于把线上坏例和离线 dataset 连起来
- 方便对 prompt、route、retrieval 改动做对比

项目映射：

- 这个项目明确把 Langfuse 放在 truth layer 里，但不会把某个 UI 页面是否显示正文当成唯一验收标准

常见追问：

- 你如何设计 score
- Langfuse 和普通日志平台的差别是什么

### 48. 你怎么做 prompt 优化

短答：

> 先抓真实坏例，再沉淀 dataset，对比策略改动前后行为，不做盲改 prompt。

展开：

- prompt 优化最怕凭感觉
- 真实坏例比主观灵感更重要
- 调 prompt 时要同步看副作用，不然容易修一处坏三处

项目映射：

- 这个项目倾向先看 trace 和回归样本，再决定是改 route 合同、改 retrieval 还是改 prompt

常见追问：

- prompt 优化和 schema 优化哪个先做
- 你怎么防止 prompt 越写越长

### 49. eval 数据集怎么构建

短答：

> 从真实坏例和关键主链场景出发，先做小而准的数据集，再逐步扩。

展开：

- 数据集不需要一开始很大
- 但必须覆盖首轮、follow-up、检索、降级和典型失败场景
- 样本要能支撑回归，而不是只展示 happy path

项目映射：

- 这个项目已经把最小正式数据集扩到首轮、同 session follow-up、retrieval quote case

常见追问：

- 合成数据能不能用
- 数据集多久更新一次

### 50. LLM-as-Judge 怎么看

短答：

> 能用，但不能盲信；更适合做辅助评分，不适合单独当最终真相。

展开：

- Judge 模型也会偏
- 它对格式、措辞很敏感
- 最稳的做法是代码断言、结构化检查、人工 spot check、LLM judge 组合使用

项目映射：

- 这个项目当前更重 Go 合同测试和结构化回归，而不是把质量完全交给主观 judge

常见追问：

- 哪类任务最适合 LLM judge
- judge prompt 怎么设计

## 10. 并发、可靠性、运行时题

### 51. Agent 系统为什么更容易遇到并发问题

短答：

> 因为它往往带状态、长链路、外部工具和多步执行，比普通请求更容易出现状态竞争和超时。

展开：

- 会话级状态可能被并发读写
- 工具调用可能顺序依赖
- 长链路更容易叠加时延和失败

项目映射：

- 这个项目已经补了 `MemoryStore` 并发隔离测试，覆盖同 session 并发创建和不同 session 并发保存不串状态

常见追问：

- 你怎么做 session 级隔离
- SSE 下并发更复杂在哪

### 52. 同一个 session 的并发消息怎么处理

短答：

> 要明确串行化、拒绝并发、或做版本化合并，不能默认并发安全。

展开：

- 最稳的是同 session 串行执行
- 如果允许并发，就要定义版本冲突策略
- 否则很容易出现晚到结果覆盖早到状态

项目映射：

- 这个项目按 `session_id` 管理会话状态和快照，就是为了避免多轮执行互相踩踏

常见追问：

- 如果用户连续狂点发送怎么办
- 允许并发的收益是什么

### 53. 你怎么处理工具超时

短答：

> 设置分层超时、记录失败原因、必要时降级，不让单工具无限拖垮整轮。

展开：

- 工具超时要和模型超时分开看
- 部分工具失败可以降级继续
- 高价值路径要明确超时后的用户提示

项目映射：

- 这个项目里检索 0 命中和执行错误已经区分处理，不会把所有失败都混成一种 `agent_error`

常见追问：

- 超时后重试几次
- 幂等和超时策略怎么配

### 54. 幂等为什么重要

短答：

> 因为 Agent 系统常常要重试，没有幂等保护，副作用会被重复执行。

展开：

- 幂等是防重复写、防多次扣费、防重复发消息的基础
- 即使当前系统读多写少，也要养成这个意识
- 一旦接入外部业务动作，幂等是必须项

项目映射：

- 这个项目当前主要是解读和检索，但如果后续接入外部写操作，必须把幂等和审计前置

常见追问：

- 幂等 key 怎么设计
- 重试和幂等的关系是什么

### 55. 你怎么处理长链路部分失败

短答：

> 先定义哪些节点可降级，哪些节点必须终止，再把失败原因结构化暴露出来。

展开：

- 不是所有失败都该整轮报错
- 也不是所有失败都该偷偷忽略
- 核心是明确失败层级和用户可感知策略

项目映射：

- 这个项目就把“artifact 缺失”“检索 0 命中”“动态口径冲突”分成了不同处理策略

常见追问：

- 哪些失败你会继续答
- 怎么避免静默错误

### 56. 你怎么看 durable execution

短答：

> 对长时任务和外部等待很重要，但不是所有 Agent 项目一开始都要上重型工作流引擎。

展开：

- durable execution 解决崩溃恢复、等待人工输入、长时间任务续跑
- 但也会引入较重基础设施和心智负担
- 早期应先看需求是否真的需要

项目映射：

- 这个项目当前更强调 manager-owned contract 和 session 恢复，还没有上重型 durable workflow

常见追问：

- 什么场景你会引入 Temporal 这类系统
- 不上 durable execution 的代价是什么

### 57. 为什么流式输出会增加工程复杂度

短答：

> 因为流式输出不只是 UI 体验问题，它会影响状态提交、错误恢复和中途取消。

展开：

- 你要定义何时 flush、何时 done
- 中途出错要不要保留已输出片段
- 还要考虑 tool_call、thinking、component 这类结构化事件

项目映射：

- 这个项目用 SSE 输出 `thinking / tool_call / component / text / error / done` 六类事件

常见追问：

- 前端如何恢复流式中断
- 流式输出会不会让 trace 更复杂

## 11. Guardrails 与安全题

### 58. guardrails 是什么

短答：

> guardrails 是程序化保护栏，用来限制输入、route、tool 和输出越界，不是最后补一句提示词。

展开：

- guardrails 可以在输入前、执行中、输出前多个位置出现
- 它们解决的是“系统能不能这样做”，不是“模型想不想这样做”
- 早拦截比晚补救更稳

项目映射：

- 这个项目不仅有 final guard，还有 Policy Gate 和 preflight 这类更早的保护层

常见追问：

- guardrails 和 moderation 有什么关系
- prompt guard 算不算 guardrail

### 59. 为什么 final guard 不够

短答：

> 因为很多问题应该在更早阶段阻断，等到最终输出再拦已经太晚。

展开：

- 权限不足应该在动作前拦
- 缺资料应该在执行前拦
- 高风险工具不该等输出阶段才发现

项目映射：

- 这个项目里 `final_guard.go` 负责最后收口，但 artifact 和策略边界很多是在前面处理的

常见追问：

- final guard 最适合拦什么
- 哪些东西不该交给 final guard

### 60. 你怎么防 prompt injection

短答：

> 把外部文本当不可信输入，分层处理系统指令、用户输入和检索内容，并限制外部内容直接驱动高风险工具。

展开：

- 注入本质是非可信文本试图改写系统策略
- 所以关键不是“叫模型别信”，而是把信任边界做出来
- 外部内容最好只能作为证据，不应直接拥有控制权

项目映射：

- 这个项目坚持“检索归知识库，最终解释归 runtime”，就是在做边界隔离

常见追问：

- 检索内容里如果有恶意指令怎么办
- tool schema 能防多少注入

### 61. 高风险工具怎么控

短答：

> 更窄的 schema、更强的鉴权、更严格的幂等、更明确的人工确认。

展开：

- 高风险工具不能只是“给个工具描述”
- 最好带上权限校验、参数验证和审计日志
- 必要时拆成“生成建议”和“真正执行”两步

项目映射：

- 这个项目暂时以解读为主，但它的设计原则已经是“高风险动作不能只靠 LLM 决定”

常见追问：

- 什么算高风险
- 是否要做风险分级

### 62. 你怎么做输出边界控制

短答：

> 先定义不能说什么、不能漏什么，再做结构化检测和最终断言。

展开：

- 输出边界不只是脏词过滤
- 还包括内部 prompt、trace_id、tool_call、系统私有字段泄漏
- 这类边界最好做成程序断言，不只靠 prompt

项目映射：

- 这个项目已经增强 final guard，拦截明确泄漏 `system prompt`、`trace_id`、`tool_call` 的内容

常见追问：

- 误杀怎么办
- 输出边界如何评测

## 12. 生成式系统工程化题

### 63. 生成式系统和传统后端最大的不同是什么

短答：

> 传统后端主要管确定性逻辑，生成式系统还要管理概率性行为。

展开：

- 同样输入未必总是同样输出
- 所以工程重点会转向合同、guard、dataset、trace 和回归
- “能跑”不等于“可上线”

项目映射：

- 这个项目后期的重点就是把自由生成收口到结构化合同和程序 renderer 上

常见追问：

- 概率性行为怎么回归
- 什么时候要引入 deterministic layer

### 64. 为什么说 Agent 项目本质上是系统工程

短答：

> 因为它同时涉及模型、工具、状态、检索、观测、评测和安全边界。

展开：

- 单看模型输出会低估大量工程复杂度
- 真正难的是跨层协同和失效模式
- 任何一个环节弱，都可能把整条链拖垮

项目映射：

- 这个项目的真实价值就在于把 runtime、trace、retrieval、session、guard 接成了一条可验证主链

常见追问：

- 这和普通 AI demo 差别在哪
- 哪层最容易被忽略

### 65. 你怎么平衡质量、成本、时延

短答：

> 先保主链稳定，再用 cheap gate、受控检索、bounded specialist 和分层模型策略做优化。

展开：

- 质量优先时，允许多一点结构化步骤
- 成本优先时，先砍无效调用和无效重跑
- 时延优先时，先看高频路径是否能复用

项目映射：

- 这个项目通过 cheap gate 和 follow-up 资产复用，减少了普通追问重跑全链的开销

常见追问：

- 你会先优化哪个
- 是否做多模型分层

### 66. 你怎么避免过度框架化

短答：

> 先把主链跑通，再只为真实问题加抽象，不为“未来可能会用”预埋过多层。

展开：

- Agent 领域很容易被框架名带偏
- 过早抽象会让排障和 onboarding 都变难
- 简单、可观测、可验证比“模式很多”更重要

项目映射：

- 这个项目后期就在持续删除 legacy path，收口到一条 manager-owned runtime 主链

常见追问：

- 你怎么看 LangGraph / ADK / 自研
- 什么迹象说明你过度设计了

## 13. 场景题与 system design 深挖

### 67. 如果线上发现回答突然变空泛，你怎么排查

短答：

> 先看 route 和 retrieval 是否退化，再看 prompt / compose / final guard 是否误伤。

展开：

- 第一步查 trace，确认主链有没有变
- 第二步查 retrieval 命中和证据消费
- 第三步查是不是 fallback 或 guard 命中过多
- 最后才看模型和 prompt

项目映射：

- 在这个项目里，我会优先看 `ExecutionSnapshot`、retrieval quote case、cheap gate 命中和 final guard 拦截情况

常见追问：

- 如何快速判断是模型问题还是系统问题
- 线上无坏例数据怎么办

### 68. 如果面试官说“RAG 命中很多，但答案还是不对”，你怎么答

短答：

> 这通常不是纯召回问题，而是 evidence consumption 问题。

展开：

- 先确认召回结果里是否真的有关键证据
- 再看模型是否引用了这些证据
- 还要看证据之间是否冲突、排序是否合理

项目映射：

- 这个项目的受控检索链就强调“证据返回”和“最终成文”分开，方便判断是检索错还是消费错

常见追问：

- 你如何验证消费错误
- renderer 会不会放大消费问题

### 69. 如果模型老是选错工具，你怎么修

短答：

> 先缩小工具集合和边界，再看描述、schema 和路由前置是否需要调整。

展开：

- 工具选错不一定是模型太弱
- 常见原因是工具相似、输入不清、描述太泛、上下文太噪
- 先做工具治理，再考虑多 agent 拆分

项目映射：

- 这个项目通过分域 specialist 和受限工具，把“全量工具自由选择”这类问题前置规避了

常见追问：

- 会不会是 prompt 不够强
- 如何用数据证明工具混淆

### 70. 如果用户连续发 3 条 follow-up，你怎么保证不乱

短答：

> 明确 owner、会话锁、复用策略和重跑边界，不能靠模型自己猜。

展开：

- 先控制同 session 并发
- 再定义哪类追问复用上轮结果
- 最后把当前执行快照持久化，保证恢复一致

项目映射：

- 这个项目的 cheap gate、ExecutionSnapshot 和 session 恢复就是为这类问题服务的

常见追问：

- 如果第 2 条和第 3 条语义冲突怎么办
- 要不要支持撤销上一轮

### 71. 如果面试官问“你这个系统怎么做回归”，你怎么答

短答：

> 我会讲分层回归：合同测试、最小数据集、trace 坏例、关键场景 smoke。

展开：

- 先测结构化合同是否还成立
- 再测首轮、follow-up、retrieval 等关键样本
- 最后用线上坏例回灌数据集

项目映射：

- 这个项目正式回归入口是 `make regression`，并配有 `eval/datasets` 和 `eval/reports`

常见追问：

- 为什么不是直接看人工体验
- 数据集更新节奏是什么

### 72. 如果面试官问“你这个系统怎么处理并发”，你怎么答

短答：

> 我先分 session 内并发和 session 间并发，再分别讲锁、隔离和状态一致性。

展开：

- session 内重点是防状态竞争
- session 间重点是资源隔离和可扩展
- 如果系统有 SSE，还要考虑中途取消和回放

项目映射：

- 这个项目已经补过 session 级状态并发测试，重点保证不同 session 不串状态、同 session 不重复创建独立状态对象

常见追问：

- 你如何压测这类场景
- 内存态 session 的瓶颈是什么

### 73. 如果面试官问“你怎么给这个项目继续做 RAG 提升”，你怎么答

短答：

> 我会按召回、排序、证据消费、评测闭环四层做，而不是盲目换 embedding。

展开：

- 先用坏例分出“没召回”和“没消费”
- 召回层再看 chunk、query rewrite、hybrid、rerank
- 消费层再看 prompt、结构化 evidence bundle、renderer
- 最后用 retrieval eval 和 answer eval 双闭环验证

项目映射：

- 这个项目最适合先加强 retrieval quote case、evidence bundle 对齐和知识单元切分，而不是先大动模型

常见追问：

- 你会先做哪一步实验
- 如何避免优化一处拖垮时延

### 74. 如果面试官问“你这个项目离生产还差什么”，你怎么答

短答：

> 当前更像可信学习型原型，离生产还差权限体系、审计、容量治理、更系统的线上指标和更大规模 eval。

展开：

- 当前主链和边界已经比较清楚
- 但生产还要看多租户、鉴权、队列、限流、稳定部署、容量预案、值班排障
- 还需要更大的真实数据和更成熟的质量基线

项目映射：

- 这个项目已经把 runtime、trace、retrieval、guard 收口，但没有把大型生产化设施都做完

常见追问：

- 如果只能补三项，你补哪三项
- 现在最脆弱的一层是什么

## 14. 项目题：suanming-agent

### 75. 这个项目最核心的架构选择是什么

短答：

> 让 `Manager` 成为 runtime 内唯一 conversation owner，并把 route、execution contract、specialist 执行分层。

展开：

- 这样能稳定承接多轮对话
- 也能避免 specialist 各自抢答
- 还方便做 follow-up 复用和最终统一 compose

项目映射：

- 主链已经稳定在 `RouteAdvisor -> Policy Gate -> Manager -> ExecutionPlan -> Prefill -> specialist runner(s) -> manager compose -> final guard -> SSE`

常见追问：

- 为什么不是 route 后直接执行
- 如果以后做更多领域，这套结构还稳吗

### 76. 为什么 route 不直接等于执行

短答：

> 因为 route 只回答“理解成什么”，执行还要回答“需要哪些 artifact、是否复用、是否重跑、最终怎么收口”。

展开：

- route 偏理解层
- execution plan 偏合同层
- 两者混掉后，执行层就会出现隐式判断和不可控分支

项目映射：

- 这个项目专门把 route approval 和 execution plan 拆开，就是为了清边界

常见追问：

- route 最少应该产出哪些字段
- execution plan 应不应该持久化

### 77. `ExecutionPlan` 在这个项目里的作用是什么

短答：

> 它是 route 进入执行层后的正式合同，显式承载 domains、required artifacts 和 follow-up mode。

展开：

- 有了它，执行层不用再偷偷猜
- 也更方便 trace、debug、session 恢复和回归
- 它是 manager-owned runtime 的核心结构之一

项目映射：

- 项目里 follow-up 的 `direct / reuse_artifact / rerun_specialist` 都应该先落进 plan，再由后续层消费

常见追问：

- plan 是静态还是动态生成
- 多域时 plan 怎么表示优先级

### 78. 为什么 `Prefill` 要程序做

短答：

> 因为命盘和确定性前置产物更适合程序准备，稳定、可复现、便于复用。

展开：

- 排盘不是 LLM 的长项
- 程序准备 artifact 可以减少模型自由发挥
- 还能支撑 follow-up 复用和缓存

项目映射：

- 这个项目按 `RequiredArtifacts` 做 prefill，不再只按 `primary_domain` 猜

常见追问：

- prefill 放太多逻辑会不会变重
- 哪些东西不该 prefill

### 79. 为什么要做 controlled retrieval

短答：

> 因为检索如果完全自由，系统很快会变成不可解释的黑盒。

展开：

- 自由检索会带来时延、成本和来源污染
- 受控检索能让证据链更清楚
- 也方便做 retrieval eval 和 bad case 定位

项目映射：

- 这个项目把知识检索定位为证据提供，不让知识库直接替 runtime 写最终答案

常见追问：

- 你怎么定义“受控”
- 会不会限制模型发挥

### 80. 这个项目为什么不是一个简单 demo

短答：

> 因为它不是只做页面聊天，而是把 runtime 主链、artifact、follow-up、retrieval、trace、regression 接成了闭环。

展开：

- demo 往往只展示 happy path
- 这个项目明确处理了 follow-up、0 命中、guard、session 恢复和并发隔离
- 它更像“可验证学习型原型”，不是“页面会动”

项目映射：

- 项目里有 `eval/datasets`、`eval/reports`、`make regression`、`ExecutionSnapshot`、cheap gate 样本沉淀这些工程化要素

常见追问：

- 你最能证明工程性的证据是什么
- 为什么还不叫生产系统

### 81. 这个项目离生产还差什么

短答：

> 差更完整的权限体系、审计、容量治理、线上指标、真实用户闭环和更大规模 eval。

展开：

- 当前主链已清晰，但生产不只看主链
- 还要看多租户、鉴权、运营、变更治理、告警和容量预案
- Agent 项目里，质量体系和安全体系一样重要

项目映射：

- 这个项目已经把核心架构和学习闭环搭好，但还没补完大型生产设施

常见追问：

- 如果只能补三项你怎么排序
- 你最担心哪类线上故障

## 15. 贡献与协作题

### 82. 这是 AI 协作开发的项目，你怎么讲自己的贡献

短答：

> 我不会说“全手写”，但会明确说我主导的是架构收口、问题定位、回归设计、边界决策和最终验收。

展开：

- AI 可以加速实现，但不会替代系统判断
- 真正体现工程能力的是：知道该让 AI 写什么，不该让 AI 决定什么
- 我会把贡献落到关键主链、关键故障和关键权衡上

项目映射：

- 这个项目里更能体现贡献的，不是某一段 prompt，而是 manager-owned runtime、follow-up 收口、retrieval 边界、trace / eval 体系

常见追问：

- 你具体改过哪些关键问题
- 你如何验证 AI 生成代码没带来隐患

### 83. 你最自豪的设计是什么

短答：

> manager-owned runtime，因为它把 owner、contract、artifact、follow-up 和最终收口统一到了一个可控主链。

展开：

- 它不是一个炫技点
- 它直接决定了多轮稳定性和排障清晰度
- 没有 owner 统一，后面很多优化都做不稳

项目映射：

- 这条主链最终落成了 `RouteAdvisor -> Policy Gate -> Manager -> ExecutionPlan -> Prefill -> specialist runner(s) -> manager compose -> final guard -> SSE`

常见追问：

- 这个设计最大的代价是什么
- 如果让你重做，会不会还这么选

### 84. 如果重做一次，你会先做什么

短答：

> 先定 owner、route、execution contract，再做最小主链和最小回归，不会一开始就堆多 Agent。

展开：

- 很多项目一开始就掉进“能力很多、边界很乱”的坑
- 我会优先建立可验证骨架
- 后面再逐步加 retrieval、cheap gate、trace 和评测

项目映射：

- 这个项目后期其实就是在往这个方向回收复杂度

常见追问：

- 你最后悔最早没做什么
- 如果时间只给两周你会怎么收口

### 85. 你怎么和 AI 协作才不失控

短答：

> 先定边界和验收，再让 AI 生成实现；关键路径靠代码、trace 和测试回看，不直接相信生成结果。

展开：

- 先让 AI 写边界模糊的问题，通常会越写越散
- 正确方法是我先定义目标、失败条件和验证方式
- AI 更适合加速实现和备选方案生成，不适合代替系统判断

项目映射：

- 在这个项目里，很多关键改动都要回到真实 runtime 主链、真实 trace、真实 regression 去验

常见追问：

- 你怎么审 AI 生成代码
- 什么时候 AI 反而会拖慢你

## 16. 最后必背的 12 句

1. route 不等于 execution contract
2. owner 边界比 agent 数量更重要
3. workflow 外壳加少量 agent 决策点，通常比全自主更稳
4. 高风险动作不能只靠 LLM 决定
5. RAG 重点是证据控制，不是搜得越多越好
6. retrieval 对了，答案也可能错，因为 evidence consumption 也会出问题
7. Eval 要分层，不只看最终文案
8. trace 是系统真相的一部分，不只是调试日志
9. follow-up 的核心不是带历史，而是复用策略
10. 并发问题本质上是状态边界问题
11. 生成式系统的核心不是更聪明，而是更可控
12. `suanming-agent` 最重要的设计是 manager-owned runtime 主链
