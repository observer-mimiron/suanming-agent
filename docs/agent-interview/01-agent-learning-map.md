# Agent 学习地图

结论：面试准备不要从框架 API 开始，要先把“什么时候该用 Agent、系统怎么控住、怎么证明它可靠”这三件事学顺。

## 1. 先记住面试官真正在看什么

截至 **2026-07-18**，主流公开工程资料的共同结论很一致：

- OpenAI 强调先从最简单可行流程开始，再逐步加工具、检索和多 Agent
- Anthropic 强调很多场景里，workflow 比 fully autonomous agent 更稳
- Langfuse 这类观测工具强调 trace、dataset、score 闭环，而不是只看聊天日志

所以面试不该只背框架名，核心是 5 个判断：

1. 这是不是 Agent 问题
2. 单 Agent、workflow、多 Agent 怎么选
3. 工具、状态、检索怎么约束
4. 出错了怎么降级
5. 效果怎么评测和优化

再往前一步，面试官实际也在看你有没有工程脑子。你回答任何 Agent 方案时，脑子里最好都同时带着这 9 个维度：

1. reliability（稳定性和失败恢复）
2. latency（时延和响应体验）
3. cost（token、工具调用、重试成本）
4. state（会话内状态承接）
5. memory（跨轮或跨会话长期记忆）
6. tool contracts（工具输入输出合同）
7. observability（trace、日志、指标、session）
8. eval（离线样本、回归、线上坏例）
9. security（权限边界、提示注入、数据泄露）

## 2. 先把这 10 个基础概念讲清楚

### 2.1 Agent（运行时动态决定下一步的执行体）

面试可直接说：

> Agent 不是“会思考的机器人”，而是运行时会根据上下文决定下一步动作的系统节点。这个动作可能是回复、调用工具、检索知识，或者把任务交给下游执行单元。

### 2.2 Workflow（代码预先写死步骤的流程）

面试可直接说：

> Workflow 的路径主要由代码决定，适合稳定、高可控场景。很多生产系统不是纯 Agent，而是 workflow 外壳里嵌少量 Agent 决策点。

### 2.3 Tool Calling（模型通过结构化接口调用工具）

关键点：

- 它解决的是“让模型接外部能力”
- 不等于“模型真的理解业务”
- 工具越多，越要做权限、参数、结果边界

### 2.4 Routing（先判断请求该走哪条链）

关键点：

- routing 适合请求差异大、领域边界明显的系统
- routing 结果不应该直接等于最终执行合同

### 2.5 Manager-Worker（主控拆解、工人执行、主控收口）

关键点：

- 适合多领域、多子任务，但又要统一对话体验的场景
- 重点不在“有几个 agent”，重点在 owner 边界

### 2.6 Handoff（执行权直接移交）

关键点：

- handoff 更像接力
- manager-worker 更像经理带团队
- 多轮复杂会话里，handoff 容易让 owner 漂掉

### 2.7 RAG（检索增强生成）

面试不要只说“先搜再回答”，要讲 4 层：

1. 何时检索
2. 怎么检索
3. 证据如何进入回答
4. 检索失败如何降级

### 2.8 State（当前会话运行态）

关键点：

- 它通常服务当前会话
- 解决的是“这一轮和上一轮怎么接”
- 例如当前领域、已拿到的 artifact、最近一次执行快照

### 2.9 Memory（跨轮或跨会话长期记忆）

关键点：

- memory 不等于聊天历史
- memory 也不等于 RAG
- memory 关注的是“长期保留什么、什么时候写入、什么时候取用”

### 2.10 Eval（评测闭环）

关键点：

- eval 不是“我感觉答案不错”
- 至少要看样本、指标、回归、线上坏例聚合

## 3. 架构模式怎么选

| 方案 | 核心差异 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| 单次 LLM 调用 | 不做动态步骤决策 | 文案生成、总结、简单问答 | 简单、便宜、稳定 | 不擅长多步任务 |
| Workflow | 步骤由代码编排 | 表单审批、固定 ETL、稳定业务链 | 可控、可测、易审计 | 灵活性有限 |
| Routing | 先分流再执行 | 多领域客服、多技能入口 | 主链清晰、扩展性好 | 路由错会全链错 |
| Manager-Worker | 主控统一收口 | 多领域、多工具、多轮追问 | owner 清楚、适合复杂会话 | 实现复杂度更高 |
| Handoff | 权限直接转移 | 领域完全切换的接力式场景 | 实现简单、职责直观 | 多轮追问易漂移 |
| Evaluator-Optimizer | 一轮产出后一轮校验 | 高质量写作、代码修复、复杂生成 | 能提升质量 | 成本和时延更高 |

## 4. 先背会 5 套结构化回答模板

### 4.1 通用项目题模板

适合回答：

- 你这个 Agent 项目是做什么的
- 你们为什么这么设计
- 你在里面负责什么

建议固定成 5 句：

1. 结论：先一句话说系统定位和核心方案
2. 为什么：说业务复杂度、控制要求、为什么不能只靠单次 LLM
3. 怎么做：说主链、关键模块、状态和工具怎么组织
4. 风险：说最容易失控的点和你的防守方式
5. 项目例子：落回这个仓库的真实设计或真实 bug

你可以直接套下面这版：

> 结论：这是一个 manager-owned runtime（主控统一持有对话权）的多领域 Agent 系统，不是让多个 Agent 自由聊天。  
> 为什么：因为它既要处理命理多领域分流，也要在多轮追问里保持上下文和输出边界。  
> 怎么做：先 routing，再过 policy gate，再由 manager 生成 execution plan，之后 prefill artifact、调 specialist runner，最后 manager compose 和 final guard 收口。  
> 风险：风险主要在路由误判、工具失控、follow-up 每轮重跑导致成本失控、以及最终回答泄漏内部执行细节。  
> 项目例子：这个仓库把 `ExecutionPlan`（执行合同对象）从 route 后面单独抽出来，就是为了把“该执行什么”和“怎么分流”分开。

### 4.2 架构选型题模板

适合回答：

- 为什么不用单 Agent
- 为什么不用完全 workflow
- 为什么选 manager-worker

建议固定成 5 句：

1. 结论：先说你选了什么
2. 备选：说你评估过哪几个备选
3. 核心差异：说 owner、控制力、扩展性差在哪
4. 取舍：说你牺牲了什么换来了什么
5. 项目例子：回到本仓库

### 4.3 RAG 题模板

适合回答：

- 你怎么做 RAG
- RAG 怎么优化
- 检索失败怎么办

建议固定成 5 句：

1. 结论：先说 RAG 在系统里是“证据供给”还是“答案生成”
2. 触发：什么时候检索，什么时候不检索
3. 检索：召回、排序、过滤、截断怎么做
4. 融合：证据怎么进入回答，如何避免瞎编
5. 降级：没命中、低相关、超时怎么处理

### 4.4 工程化题模板

适合回答：

- 你怎么保证稳定性
- 并发怎么处理
- 线上怎么排障

建议固定成 5 句：

1. 结论：先说系统最重要的工程目标
2. 风险面：列 2-3 个最高频故障点
3. 机制：状态、重试、限流、超时、隔离怎么做
4. 观测：trace、日志、dataset、score 怎么接
5. 项目例子：说真实监控链或真实故障修复

### 4.5 场景题模板

适合回答：

- 如果 RAG 召回很差你怎么办
- 如果并发一高 session 串了怎么办
- 如果评测分数掉了怎么办

建议固定成 5 步：

1. 先定问题类型：质量问题、性能问题、状态问题、工具问题
2. 先拿证据：trace、日志、样本、线上坏例
3. 再拆链路：输入、路由、执行、工具、输出分别检查
4. 先做最小修复：先堵住最可能的主因
5. 最后补回归：补数据集、补断言、补可观测信号

## 5. 学这个仓库前要先带着哪些问题看

你看 `suanming-agent` 时，重点不是“算命”，而是带着下面 8 个问题去看：

1. 为什么 route 不直接等于执行
2. 为什么 `Manager` 要成为唯一 conversation owner
3. 为什么 `ExecutionPlan` 要单独存在
4. 为什么 artifact 要程序 prefill
5. 为什么检索要受控，而不是让模型自由搜
6. 为什么 final guard 不能替代前面的边界控制
7. 为什么 follow-up 不能每轮都重跑整条大链
8. 为什么真相层要靠 trace 和回归，不靠 UI 观感

## 6. 工程化学习维度要怎么学

这一节是面试加分区。很多人会讲 prompt、agent、RAG，但答不到“怎么把系统做稳”。你可以按下面 8 个维度学，每个维度都用“定义 / 常见问题 / 这个项目怎么做 / 面试怎么答”四步去记。

### 6.1 reliability（稳定性和失败恢复）

你要会讲：

- 什么算失败：模型失败、工具失败、检索失败、状态失败、输出越界
- 怎么降级：fallback、保守回答、短路澄清、终止执行
- 怎么防回归：合同测试、smoke、坏例回放

这个项目里你至少要能举 3 个例子：

1. route 有降级链，不只靠单一路由结果
2. authority-first 检索 0 命中时，不直接整轮报错
3. final guard 会拦截越界输出，但不替代前置控制

### 6.2 latency（时延和响应体验）

你要会讲：

- 时延来自哪里：模型推理、工具调用、检索、串行链太长
- 怎么控：减少不必要步骤、做 cheap gate、减少重跑、限制工具次数
- 用户感知怎么优化：SSE 分段输出、thinking 可见、慢步骤前移提示

这个项目最值得记的是：

1. follow-up 不是默认每轮重跑大链
2. cheap gate 会复用已知结果，减少一次完整 supervisor 路由
3. SSE 把过程拆成结构化事件，用户不会一直干等

### 6.3 cost（token、工具调用、重试成本）

你要会讲：

- 成本不只是模型单价，还包括上下文长度、工具次数、失败重试
- 降成本的方法通常是少跑、短上下文、少重试、少无效检索
- 成本优化不能破坏答复质量和边界控制

面试可直接说：

> 成本优化最有效的通常不是换更便宜模型，而是减少不必要的执行链，比如减少重复 routing、限制检索次数、只把必要证据注入上下文。

### 6.4 state（会话内状态）

你要会讲：

- state 记录什么：领域、artifact、最近执行快照、recent turns
- 为什么不能只靠聊天历史：历史太长、太脏、不可控
- 状态怎么防串：按 session 隔离、并发保护、显式生命周期

这个项目要记住：

1. `Manager` 统一持有对话主控权
2. `ExecutionSnapshot`（执行快照合同）服务真实运行态，而不是 UI 幻觉
3. 已补并发隔离测试，防止不同 session 串状态

### 6.5 tool contracts（工具输入输出合同）

你要会讲：

- 工具不是“给模型随便调”
- 每个工具都应该有输入约束、输出结构、失败语义、调用上限
- 工具合同越清楚，排障和评测越容易

这个项目可举例：

1. `knowledge_search`（知识检索工具）不是自由问答，它返回 passages 证据片段
2. `ExecutionPlan` 会显式承载 required artifacts
3. bounded specialist runner 只做受限执行，不直接拥有最终回复权

### 6.6 observability（可观测性）

你要会讲：

- 只看聊天日志不够
- 至少要能看 trace、session、执行阶段、工具调用、错误点
- 好的观测不是事后补日志，而是设计时就决定看什么

这个项目里要背：

1. Langfuse 是正式 truth layer 的一部分
2. trace / session / dataset run / score 都是验收依据
3. cheap gate 有单独的可观测字段和命中样本沉淀

### 6.7 eval（评测闭环）

你要会讲：

- eval 至少分离线回归和线上坏例回放
- 指标要和真实风险对齐，不是只看“像不像”
- 评测的价值是帮助你发现退化，而不是做展示 PPT

你答的时候最好固定提这 4 个动作：

1. 建最小数据集
2. 跑回归
3. 看 trace 和分数
4. 把坏例回灌到数据集

### 6.8 security（权限边界和越权风险）

你要会讲：

- 提示注入不是唯一安全问题
- 工具越权、数据泄露、内部执行细节暴露、跨 session 污染也很常见
- 安全控制要放在 route、tool、state、output 多层

这个项目可举例：

1. policy gate 和 final guard 是两道不同边界
2. final output 不能泄漏 `system prompt`、`trace_id`、`tool_call`
3. state 和 session 不能串

## 7. 面试学习顺序

### 第 1 阶段：补概念

目标：

- 你能清楚解释 agent、workflow、RAG、state、memory
- 你不会把所有复杂系统都说成多 Agent

### 第 2 阶段：补模式判断

目标：

- 你能根据业务判断用 routing、manager-worker 还是 workflow
- 你能讲出选型背后的控制成本

### 第 3 阶段：把项目讲法练熟

目标：

- 你能把这个仓库讲成一个工程系统
- 你能把主链、边界、失败模式说清楚

### 第 4 阶段：补 RAG、Eval、Guardrails

目标：

- 你不再只会讲“接了知识库”
- 你能讲检索控制、trace、dataset、score、降级

### 第 5 阶段：刷题

目标：

- 你能在压力下快速回答
- 你不会一紧张就开始堆框架名

## 8. 9 天可执行学习计划

| 天数 | 任务 | 输出标准 |
|---|---|---|
| Day 1 | 看完本文件第 1-3 节 | 讲清 10 个基础概念和 6 种架构模式 |
| Day 2 | 看完本文件第 4 节 | 能不看稿说出 5 套结构化回答模板 |
| Day 3 | 看完本文件第 5-6 节 | 能把工程化 8 维度各讲 1 分钟 |
| Day 4 | 看项目主文档前半 | 手画系统主链，能解释每一段职责 |
| Day 5 | 看项目主文档后半 | 讲清 state、artifact、follow-up、final guard |
| Day 6 | 专练 RAG 专题 | 讲清触发、召回、排序、融合、降级 |
| Day 7 | 专练 reliability / observability / eval | 讲清 trace、dataset、score、回归闭环 |
| Day 8 | 刷题库前半 + 自录音 | 基础题、架构题、工程题每题 2 分钟 |
| Day 9 | 刷题库后半 + 模拟追问 | 项目题、场景题、反问题能连答 20-30 分钟 |

每天建议固定做 3 件事：

1. 先读 30-60 分钟
2. 再脱稿复述 20 分钟
3. 最后录音或打字模拟回答 20 分钟

如果你时间更紧，可以压成 7 天，但不要砍掉 `Day 6-9` 的 RAG、工程化、场景题训练。这几块最容易拉开差距。

## 9. 学完后的最低标准

你至少要能稳定回答这 8 个问题：

1. 什么业务不该上 Agent
2. workflow 和 agent 的边界是什么
3. 多 Agent 什么时候真有必要
4. 这个仓库为什么是 manager-owned runtime
5. `ExecutionPlan` 为什么比 route 更重要
6. 你的 RAG 为什么不只是“搜一下拼上下文”
7. 你怎么做 trace、dataset、score 闭环
8. 这个项目离生产还差什么

再提高一点，你最好还能稳定回答下面 6 个工程化高频题：

1. session 状态为什么不能只放前端
2. 为什么 tool contract 比 prompt 更能提升系统稳定性
3. RAG 召回差时，你先改 query、召回、排序，还是先加 chunk
4. 如果并发高了后 trace 看起来都正常，但用户说答案偶发串会话，你怎么排
5. 什么时候应该接受“保守回答”，而不是继续重试
6. 怎么区分“模型能力不够”和“系统编排有问题”

## 10. 面试回答时的执行纪律

这部分很重要。很多人不是不会，而是答题结构散。

你回答每道题时，强迫自己过这 5 步：

1. 先下结论，不要先铺背景
2. 再讲为什么，不要一上来列技术名词
3. 再讲怎么做，要有链路和模块
4. 再讲风险，不要把方案说成完美
5. 最后落项目例子，不要一直停留在抽象层

你回答项目题时，尽量都落到这 4 类真实证据：

1. 真实主链
2. 真实状态对象
3. 真实降级策略
4. 真实评测和观测方式
