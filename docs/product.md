# 命理大师 — 产品文档

**版本：** v1.1 MVP  
**状态：** 产品定义阶段

---

## 1. 产品概述

命理大师是一个 AI 八字命理咨询聊天应用。用户用自然语言输入出生年月日时和性别，系统自动完成八字排盘，并结合项目知识库中的命理资料对用户的具体问题给出自然语言解答。

产品的核心记忆点不是“模型很玄”，而是：

- **排盘是结构化可见的**
- **问题解答是围绕用户咨询展开的**
- **知识引用是结构化可见的**
- **Agent 过程是结构化可见的**

一句话记忆点：

**“原来一个命理 Agent 是这样一步步工作的。”**

---

## 2. 目标用户

| 用户 | 场景 | 诉求 |
|------|------|------|
| **我自己（主力）** | 学习 Agent 架构，面试展示 | 先讲清楚 Go/Eino 主线，再做 LangGraph 对照版 |
| **朋友（次要）** | 好奇玩玩 | 输入生日并提问，得到结构化排盘和针对性回答 |

---

## 3. 产品形态

一个 Web 聊天应用，单页。对话中同时展示：

- 文本回复
- 工具调用
- 八字命盘卡片
- 知识引用卡片

设计方向：

**Terminal Mystic** — 墨色背景 + 朱砂红 + 琥珀金。  
MVP 先用 Naive UI 快速搭建，后续再逐步强化视觉语言。

---

## 4. v1 MVP 功能范围

### 4.1 包含的功能

| 功能 | 描述 | 优先级 |
|------|------|--------|
| **八字排盘** | 用户输入出生年月日时+性别 → 输出四柱八字 | P0 |
| **五行分析** | 统计五行分布，标注日主 | P0 |
| **十神计算** | 计算年/月/日/时柱的十神关系 | P0 |
| **大运排盘** | 返回大运结果 | P0 |
| **命理解答** | LLM 基于排盘结果和用户问题生成自然语言回答 | P0 |
| **知识引用** | 通过项目知识库 MCP 检索命理典籍/规则页并引用 | P0 |
| **多轮信息收集** | 逐步补齐出生信息 | P0 |
| **追问复用** | 排盘后追问时复用已有命盘 | P0 |
| **咨询问答** | 用户可围绕运势、婚恋、事业等问题持续追问 | P0 |
| **结构化过程展示** | thinking / tool_call / component / text 事件可见 | P0 |
| **流式响应** | 回答文字逐步推送 | P0 |

### 4.2 明确不做

| 不做项 | 原因 |
|--------|------|
| 多 Agent 闭环 | 当前产品复杂度不需要 |
| LangGraph 主链路 | 延后到 v2 对照版 |
| 原始 CoT 展示 | 对用户价值低，也不稳 |
| 复杂工作流引擎 | MVP 先不要 |

---

## 5. v2 对照版目标

v2 不是新产品，而是同一产品域的**LangGraph 对照实现**。

它要回答的问题是：

- 哪些状态编排用 Go 手写已经开始吃力
- LangGraph 在条件边、复杂路由、reasoning flow 上能补什么
- 引入双栈后，复杂度和收益是否匹配

所以 v2 的核心不是“功能更多”，而是“边界更清楚、对比更有教学价值”。

---

## 6. 用户交互流程

```text
用户打开页面
  → 看到欢迎语
  → 输入出生信息和问题
  → 系统逐步展示：
    1. thinking：正在识别出生信息
    2. tool_call：调用 bazi_calc
    3. component：八字命盘卡片
    4. tool_call：调用 knowledge_search
    5. component：知识引用卡片
    6. text：流式命理解答
  → 用户继续追问：“今年运势怎么样？”
  → 系统复用已有命盘继续分析
```

---

## 7. 成功标准

| 标准 | 验证方式 |
|------|---------|
| 用户输入出生信息后能看到完整命盘卡片 | 单元测试 + 手动验证 |
| 排盘结果正确 | 已知案例比对 |
| 系统能围绕用户具体问题作答，而不只是展示命盘 | 手动验证 |
| 知识引用来自项目知识库 MCP | 手动验证引用来源 |
| 追问时默认复用已有命盘 | 浏览器联调 |
| 能讲清楚 Go/Eino 主线如何工作 | 面试场景 |
| 能进一步讲清楚为什么 LangGraph 放到 v2 更合理 | 面试场景 |
